# ขั้น 2 · service

**หนึ่งใบสั่ง = หนึ่ง operation ของหนึ่งตาราง** ไม่ใช่ทั้งโมดูลรวดเดียว

`list` ของ `pet_species` คือหนึ่งใบ · `create` คืออีกใบ
ทำทั้งโมดูลรวดแล้วเทสตกสามข้อพร้อมกัน จะไม่รู้ว่าอันไหนพังเพราะอะไร

---

## ถามก่อนลงมือ ทุกครั้ง

**ใบสั่งไม่ได้ระบุว่า operation ไหน → ถาม แล้วหยุดรอ** ห้ามเดาว่าทำทั้งชุด

```
ตารางไหน · operation ไหน
```

| operation | ทำอะไร | ต้องมีอะไรก่อน |
|---|---|---|
| `list` | คืนหลายแถว · ค้น กรอง เรียง | — ทำก่อนได้เลย |
| `getById` | คืนแถวเดียว หรือ error ถ้าไม่มี | — |
| `create` | เพิ่มแถว | ควรมี `list` หรือ `getById` แล้ว ไม่งั้นเทสต้องอ่าน db ตรง |
| `update` | แก้แถว | `getById` |
| `delete` | ลบ (soft หรือ hard ตามตาราง) | `getById` |
| `move` | ย้ายลำดับ | `list` · **เฉพาะตารางที่มี `sortOrder`** |

**ตัวที่พึ่งตัวอื่นแล้วตัวนั้นยังไม่มี** → บอกผู้ใช้ว่าควรทำอะไรก่อน แล้วรอ
ไม่ใช่แอบทำตัวที่ขาดพ่วงไปด้วย

### ถามด้วยว่าหน้าจอต้องได้อะไร — ไม่ใช่ว่าหน้าจอหน้าตายังไง

service ที่หน้าจอเรียกไม่ได้ คือ service ที่ต้องเขียนสองรอบ · แต่ถามลึกถึงหน้าตา
จะได้ service ที่ล็อกกับหน้าที่ยังไม่มีใครอนุมัติ แล้วพอหน้าเปลี่ยนก็ต้องแก้ตาม

**เส้นแบ่ง: ถามสัญญา ไม่ถามการจัดวาง**

| ถาม | ไม่ถาม |
|---|---|
| ลิสต์แบ่งหน้าไหม | ตารางมีกี่คอลัมน์ |
| ค้นด้วยอะไรได้ · กรองด้วยอะไรได้ | ช่องค้นอยู่ตรงไหน |
| ต้องได้ฟิลด์อะไรกลับไป · ต้องพ่วงข้อมูลตารางอื่นมาด้วยไหม | ฟิลด์ไหนโชว์ ฟิลด์ไหนซ่อน |
| แก้ทีละฟิลด์ หรือส่งมาทั้งก้อน | ฟอร์มเป็น dialog หรือหน้าเต็ม |

**สคีมาไม่ได้ตอบเรื่อง paging ให้** — `sortOrder` บอกว่าตารางมีคอลัมน์ลำดับ
ไม่ได้บอกว่าหน้าจอจะให้ลาก · จัดลำดับด้วยการพิมพ์เลขก็ได้ แล้ว paging ก็ยังทำได้

**ถามตรง ๆ ว่า "หน้านี้จะลากจัดลำดับไหม"** แล้วผลตามมาเอง:
ลากได้ → ไม่มี paging (ลากข้ามหน้าไม่ได้) · `list` คืนทั้งหมดพร้อมเพดาน · ต้องมี `move`
ไม่ลาก → `list` รับ page/pageSize และต้องคืนจำนวนแถวทั้งหมดมาด้วย

เกิดจริง 2026-08-26: เขียน `list` โดยอนุมานจาก `sortOrder` ว่าไม่มี paging
แล้วเขียน comment ว่า "ตัดสินแล้ว" ทั้งที่ไม่มีใครตัดสิน — ผู้ใช้ต้องถามเองว่าถามหรือยัง

## อ่านก่อน ทุกครั้ง

| ไฟล์ | เอาอะไรจากมัน |
|---|---|
| `docs/standards/naming.md` | ชื่อฟังก์ชัน · ตัวแปร · ไฟล์ |
| `apps/api/prisma/schema/<domain>.prisma` | `///` บนหัว model บอกกฎที่รอ service มาบังคับ |
| `docs/standards/auth.md` | ใครเป็นคนเรียก · เจ้าของสัตว์กรองด้วย account id ไม่ใช่ด้วย permission |
| service ของตารางข้างเคียง | ตัวที่ทำไปแล้วเขียนไว้ยังไง |

**`///` ในสคีมาคือสเปกของขั้นนี้** — ขั้น schema เขียนกฎไว้ว่า "บังคับที่ service"
เช่น ห้ามลบตัวแม่ที่มีลูก · แถวใหม่ขึ้นบนสุด · revoke session ตอนเปลี่ยน role
**อ่านให้ครบก่อนเขียน** ไม่ใช่เขียนเสร็จแล้วมาดูว่าตกอะไร

### สำรวจสคีมาก่อนลงมือ — สามคำสั่ง ห้ามข้าม

`///` เขียนโดยคน จึงตกได้ · **สามบรรทัดนี้ถามฐานเอง ไม่ได้ถามความจำใคร**

```bash
# 1. ใครชี้มาที่ตารางนี้ — ตัวที่ delete ต้องตรวจก่อนลบ
grep -n "<Table>\b" apps/api/prisma/schema/*.prisma | grep -v "///"

# 2. ตารางนี้ชี้ไปที่ใคร — ตัวที่ create/update ต้องตรวจว่ามีจริง
sed -n '/^model <Table>/,/^}/p' apps/api/prisma/schema/*.prisma | grep -E "Id\s+BigInt"

# 3. กฎที่ `///` สั่งไว้ — ต้องมีเทสครบทุกข้อ
sed -n '/^model <Table>/,/^}/p' apps/api/prisma/schema/*.prisma | grep "///"
```

**ผลจากข้อ 1 บอกว่า `delete` ต้องทำอะไร**

| FK ที่ชี้มา | delete ต้องทำ |
|---|---|
| **บังคับ** (`BigInt`) | ลูกที่ยังไม่ลบ → ปฏิเสธ `IN_USE` · ลูกที่ลบแล้ว **ล้างไม่ได้** ปล่อยชี้ค้าง |
| **ว่างได้** (`BigInt?`) | ลูกที่ยังไม่ลบ → ปฏิเสธ · ลูกที่ลบแล้ว → เซ็ต null |

**ผลจากข้อ 2 บอกว่า `create`/`update` ต้องทำอะไร** — ตรวจว่าแม่มีจริงและยังไม่ถูกลบ
ไม่ตรวจแล้วฐานปฏิเสธด้วย FK error ซึ่งออกไปเป็น 500 คนกรอกฟอร์มเห็น "ระบบขัดข้อง"

เกิดจริง 2026-08-26: กฎ "ลบสาขาที่มีพนักงานไม่ได้" เขียนไว้ใน `///` ตั้งแต่ขั้น schema
แต่ตอนทำ service ไม่มีใครไล่ว่ามีตารางไหนชี้มาที่ `branch` บ้าง — ผู้ใช้ต้องถามเอง

## ด่าน 1 · เทสแดงก่อน

**ห้ามเขียนโค้ด service ก่อนมีเทสที่แดง** — เทสที่เขียนทีหลังคือเทสที่เขียนให้ผ่าน
โค้ดที่มีอยู่ ไม่ใช่เทสที่บอกว่าโค้ดควรทำอะไร

ไฟล์อยู่ที่ `apps/api/test/integration/<table>.<operation>.test.ts`

**integration test แตะฐานจริง** ไม่ mock — Prisma กับ Postgres คือส่วนที่พังจริง
mock แล้วเทสเขียวทั้งที่ query ผิด คือเทสที่ไม่ได้ทดสอบอะไรเลย

```bash
bun test ./test/integration/<ไฟล์>.test.ts --preload ./test/setup.ts
```

**ต้องเห็นแดงก่อน** ถ้าเขียวตั้งแต่แรก แปลว่าเทสไม่ได้ทดสอบสิ่งที่คิด

### เทสหนึ่งไฟล์ต้องมีอะไร

```
happy case        ทำสำเร็จ · ค่าที่ได้ตรงกับที่คาด
เคสปฏิเสธ         สิ่งที่ต้องไม่ผ่าน — ชื่อซ้ำ · ไม่มี id นั้น · ลบตัวแม่ที่มีลูก
เคสขอบ            ลิสต์ว่าง · ค่าที่ยาวสุด · แถวที่ถูก soft delete
```

**assert `error.code` ห้าม assert ข้อความ** — ข้อความเปลี่ยนได้ รหัสไม่เปลี่ยน

**ชื่อ `describe` และ `test` เป็นไทย และบอกงาน ไม่ใช่ชื่อฟังก์ชัน**
`ชนิดสัตว์ · ดูรายการ › ไม่คืนแถวที่ถูก soft delete` — รูปเต็มอยู่ใน `docs/standards/naming.md`

### รายงานว่าเทสไหนช้า

```bash
bun run test:report              # ทั้งชุด
bun run test:report pet          # เฉพาะไฟล์ที่ชื่อมีคำนี้
```

บอกเวลารวมต่อไฟล์ แล้วไล่เทสที่เกิน 100 ms · **เทสตัวแรกของแต่ละไฟล์ช้าเป็นปกติ**
เพราะต้องต่อฐานก่อน ให้ดูตัวที่ไม่ใช่ตัวแรก

**เคสที่ `///` สั่งไว้ต้องมีเทสทุกข้อ** — กฎที่เขียนในสคีมาแต่ไม่มีเทส คือกฎที่ไม่มีอยู่จริง

## ด่าน 2 · เขียนให้เขียว

**business logic อยู่ที่ชั้นนี้ที่เดียว** — ไม่ใช่ที่ route ไม่ใช่ที่หน้าเว็บ
route แปลง HTTP เป็นการเรียก service แล้วแปลงผลกลับ ไม่ตัดสินอะไรเอง

ไฟล์อยู่ที่ `apps/api/src/modules/<module>/<module>.service.ts`

### service ยืม service ของโมดูลอื่นได้

**เจ้าของกฎคือโมดูลที่เป็นเจ้าของตาราง** — โมดูลอื่นเรียกใช้ ไม่ก๊อปโค้ดไปเขียนเอง

`user.service` เปลี่ยน `roleId` แล้วต้องเพิกถอนเซสชัน → เรียก
`userSession.service.revokeAllOfUser()` **ไม่ใช่** `db.userSession.deleteMany()` เอง
ก๊อปเมื่อไหร่ วันที่กฎการเพิกถอนเปลี่ยน จะมีสองที่ที่ต้องแก้ แล้วจะแก้ไม่ครบ

**สามข้อที่ต้องระวัง**

**1 · ทรานแซกชันต้องเป็นอันเดียวกัน** — ยืม service มาแล้วมันเปิดทรานแซกชันของตัวเอง
แปลว่า `update` สำเร็จแต่ `revoke` ล้มเหลวได้ แล้วเหลือคนที่ถือสิทธิ์เก่าอยู่
**ฟังก์ชันที่ตั้งใจให้ยืม ต้องรับ `tx` เข้ามาได้** และคนเรียกส่ง `tx` ของตัวเองไป

**2 · ห้ามเรียกวน** — A เรียก B แล้ว B เรียก A กลับ คือ deadlock หรือ recursion ไม่รู้จบ
เรียกได้ทางเดียว · จะเรียกกลับเมื่อไหร่ แปลว่าออกแบบผิด ให้ยกกฎขึ้นไปไว้ที่คนเรียกแทน

**3 · ยืมแล้วต้องมีเทส** — เทสของ `user.update` ต้องพิสูจน์ว่าเซสชันหายไปจริง
ไม่ใช่แค่ว่า `update` คืนค่าถูก · กฎที่ยืมมาแต่ไม่มีเทสที่ฝั่งคนยืม คือกฎที่หายไปเงียบ ๆ
วันที่มีคนแก้ฟังก์ชันต้นทาง

### กฎที่ใช้กับทุก operation

**soft delete ต้องกรองเอง** — `where: { deletedAt: null }` ทุก query ที่อ่านของที่ใช้งานอยู่
รวม `include` ของ to-many ด้วย · ลืมแล้วแถวที่ลบไปแล้วจะโผล่ขึ้นมาเงียบ ๆ

**`findUnique` ห้ามใช้กับ business key** — unique ของ business key เป็น partial index
ที่ Prisma มองไม่เห็น ใช้ `findFirst` แทน

**เงินและ id เป็น string บน wire** ห้ามเป็น JSON number

**`createdBy` / `updatedBy` มาจากคนที่เรียก** ไม่ใช่ค่า default ในโค้ด

**service ฝั่งเจ้าของสัตว์กรองด้วย account id จากเซสชัน เสมอ** — ไม่ใช่ด้วย permission key
คำถามคือ "แถวไหนเป็นของคุณ" ไม่ใช่ "บทบาทนี้ทำอะไรได้" · เหตุผลเต็มอยู่ที่
`docs/standards/auth.md` · ลืมกรองแล้วเจ้าของสัตว์คนหนึ่งเห็นประวัติของอีกคน

**ทุก operation ที่เปลี่ยนข้อมูลต้องเขียน `writeAudit()`** — `create` `update` `delete` `move`
ไม่ใช่ `list` หรือ `getById`

```ts
await writeAudit(tx, {
  action: `${MODULE}.create`,   // รูปเดียวกับ permission key
  module: MODULE,
  recordId: created.id,
  after: { ...ฟิลด์ที่เกี่ยวข้อง },
  userId: actorId,
})
```

**เขียนใน `tx` เดียวกับการเปลี่ยนแปลงเสมอ** — บันทึกที่เขียนนอกทรานแซกชันจะรอดจาก
rollback แล้วยืนยันว่ามีการเปลี่ยนแปลงที่ไม่เคยเกิด

**`update` ใช้ `diffFields()` ก่อน** แล้วเขียนเฉพาะตอนที่มีอะไรเปลี่ยนจริง —
ฟอร์มส่งทุกฟิลด์กลับมาตอนกดบันทึก คนเปิดดูแล้วกดบันทึกเฉย ๆ ไม่ควรได้บันทึกหนึ่งแถว

### กฎเฉพาะ operation

**`create`** — ตารางที่มี `sortOrder`: **แถวใหม่ขึ้นบนสุด** (`sortOrder = 0` แล้ว shift ที่เหลือ)
ต้องอยู่ในทรานแซกชันเดียวกับ insert ไม่งั้นสองคนสร้างพร้อมกันแล้วได้ลำดับซ้ำ

**`delete`** — ตารางที่มีลูก: ตรวจลูกที่ **ยังไม่ถูก soft delete** ก่อน
มีอยู่ = ปฏิเสธ · ลูกที่ถูกลบแล้ว = เซ็ต FK เป็น null (ถ้าคอลัมน์ว่างได้)
**ทั้งหมดในทรานแซกชันเดียว**

**`move`** — ตารางที่มี `sortOrder` เท่านั้น · shift แถวที่คั่นกลาง ในทรานแซกชันเดียว
**ตารางที่มี `sortOrder` ห้ามแบ่งหน้า** — `list` ของมันคืนทั้งหมด มีเพดาน

**`list`** — เรียงต้องมี tiebreaker เสมอ (`[{ sortOrder: 'asc' }, { name: 'asc' }]`)
ขาดแล้วลำดับสลับเองทุกครั้งที่ refresh
