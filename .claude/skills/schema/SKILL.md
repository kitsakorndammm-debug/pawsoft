# ขั้น 1 · schema

ตารางเดียว ต่อหนึ่งใบสั่ง **ถามให้จบก่อนแตะไฟล์**

ตารางผิดตั้งแต่ต้น = service, api, หน้าเว็บ, เทส ผิดตามหมด แก้ทีหลังต้อง migrate ข้อมูลจริง
ถามห้านาทีตอนนี้ ถูกกว่าย้อนหกขั้นทีหลัง

---

## ตารางหนึ่งตัวอยู่สองไฟล์ ไม่ใช่ไฟล์เดียว

**ลืมไฟล์ที่สองคือกับดักที่แพงที่สุดของขั้นนี้** — schema ผ่าน typecheck เขียว
แต่ข้อมูลซ้ำเข้าฐานได้เงียบ ๆ เพราะไม่มีใครสร้าง index ให้

| ไฟล์ | เก็บอะไร |
|---|---|
| `apps/api/prisma/schema/<domain>.prisma` | model · field · relation · `@@index` ธรรมดา |
| `apps/api/prisma/sql/parts/` | **partial unique · CHECK · COMMENT ไทย · index มีเงื่อนไข** |

Prisma แสดง partial index (`WHERE deleted_at IS NULL`) ไม่ได้ ของพวกนี้จึงอยู่ใน SQL
`apps/api/prisma/patch.ts` เป็นตัวรัน — ผ่าน Prisma connection **ไม่ใช่ psql**
(Windows dev ไม่ต้องลง Postgres client · ฐานอยู่ใน Docker)

## audit block ชี้ไปที่ User — ตารางแรกของระบบจึงเป็นข้อยกเว้น

`createdBy` / `updatedBy` / `deletedBy` เก็บ `user.id` เสมอ ผลสองข้อ:

**1 · User ต้องมาก่อนทุกตาราง** ไม่มี User = ไม่มีใครให้ชี้ = สร้างแถวไหนไม่ได้เลย
จะทำทะเบียนก่อน User ไม่ได้ ต่อให้ทะเบียนนั้นดูง่ายกว่า

**2 · `user.createdBy` ต้องเป็น nullable — ตารางเดียวในระบบที่ว่างได้**
แถวแรกสุดของ `user` ไม่มีใครสร้าง มันคือจุดที่ทุกอย่างเริ่ม

**ห้ามแก้ด้วย `createdBy = 1` ชี้กลับหาตัวเอง** — เคยทำแบบนั้นแล้ว `db:reset` พังทุกครั้ง:
การใส่ `id` ตรง ๆ ทำให้ sequence ไม่ขยับ แถวถัดมาขอ id อัตโนมัติแล้วได้ 1 ซ้ำ
`null` แปลว่า "ไม่มีใครสร้าง" ซึ่งเป็นความจริง และมีอยู่แถวเดียวตลอดอายุระบบ

ตารางอื่นทุกตัว `createdBy` / `updatedBy` เป็น **NOT NULL** — ไม่มีข้อยกเว้นที่สอง

**`pet_owner_account` ไม่ใช่ข้อยกเว้นที่สอง** — บัญชีเจ้าของสัตว์สร้างตัวเองตอนล็อกอิน
Google ครั้งแรก มันจึงไม่มี audit block แบบตารางทะเบียนตั้งแต่ต้น ไม่ใช่มีแล้วปล่อยว่าง
รายละเอียดอยู่ที่ `docs/standards/auth.md`

## อ่านก่อน ทุกครั้ง

| ไฟล์ | เอาอะไรจากมัน |
|---|---|
| `docs/standards/naming.md` | **ชื่อ model · ตาราง · คอลัมน์ · enum** — ยาวได้ถ้าเจาะจง ห้ามกว้าง |
| `docs/standards/db-conventions.md` | audit block · `f.*` type · กฎเหล็ก |
| `apps/api/prisma/schema/<domain>.prisma` | ตารางข้างเคียงเขียนไว้ยังไง |
| `apps/api/prisma/sql/parts/` | ตารางข้างเคียงลง index แบบไหน |

**ไฟล์ไหนยังไม่มี ให้บอกผู้ใช้ ไม่ใช่เดาแทน** — ยึดตารางที่เขียนไปแล้วเป็นแบบ
และ**ถามผู้ใช้เมื่อไม่มีแบบให้ดู** ห้ามยกกฎจากโปรเจคอื่นมาโดยไม่บอกว่ายกมาจากไหน

**ห้ามก๊อปกฎจาก db-conventions มาไว้ในสกิลนี้** — ของอยู่ที่นั่นที่เดียว

## ด่าน 1 · ตรวจของเดิมก่อนเสมอ

ยังไม่ถามอะไรจนกว่าจะรู้ว่ามีอะไรอยู่ **ทั้งสี่บรรทัด ไม่ใช่แค่บรรทัดแรก**

```bash
grep -rn "model <Name>"  apps/api/prisma/schema/           # ตารางมีไหม
grep -rn "<Name>\b"      apps/api/prisma/schema/*.prisma   # ใครผูกอยู่
grep -n  -i "<table>"    apps/api/prisma/sql/parts/     # index/CHECK มีแล้วไหม
ls -1 apps/api/src/modules/ | grep -i <name>               # module มีแล้วไหม
```

**มีอยู่แล้ว** → บอกผู้ใช้ว่ามีฟิลด์อะไร · patch.sql ให้อะไรไว้ · ใครผูกอยู่
แล้วถามว่าจะแก้ตรงไหน ห้ามเขียนทับเงียบ ๆ

**ลบ model ที่มี relation ชี้เข้ามา** → นับให้ดูก่อนว่าพังกี่ไฟล์ แล้วรอผู้ใช้ตัดสิน

## ด่าน 1.5 · โหมดตรวจ

ผู้ใช้สั่ง "ตรวจ" ไม่ใช่ "เพิ่ม/แก้" → เทียบของเดิมกับ convention **แล้วรายงาน หยุด ไม่แก้**
(แก้คือใบสั่งใหม่ ผู้ใช้เป็นคนสั่ง)

ไล่ทีละข้อ ทั้งสองไฟล์:

```
schema.prisma
  □ /// comment บนหัว model
  □ audit block ครบตามชนิดตาราง (business 6 · junction 2 · log 1) และวางท้าย model
  □ createdBy/updatedBy เป็น NOT NULL — ยกเว้น user ที่ต้อง nullable
  □ soft delete → มี @@index([deletedAt])
  □ ไม่มี @updatedAt · createdBy ไม่ได้เป็น relation
  □ ไม่มี Float / Double
  □ ชนิดตรง f.* (name → VarChar(200) ฯลฯ)
  □ FK ทุกตัวมี @@index
  □ FK ว่างได้ที่ผู้ใช้บอกว่า "ห้ามลบตัวแม่" — รู้ตัวไหมว่าฐานปล่อยผ่าน (SET NULL)
  □ ไม่มี @unique เปล่า ๆ บนตารางที่ soft delete

sql/patch.sql
  □ ชื่อห้ามซ้ำ → มี partial unique WHERE deleted_at IS NULL
  □ ตารางอยู่ใน DO block catalogue แล้วหรือยัง (ดูข้างล่าง)
  □ มี sortOrder → อยู่ในลิสต์ CHECK sort_order 0..2e9
  □ มี deleted_pair CHECK
  □ COMMENT ON TABLE เป็นภาษาไทย
```

รายงานเป็นตาราง: `ตาราง | ข้อที่ไม่ผ่าน | ไฟล์:บรรทัด | ควรเป็นอะไร`
ผ่านหมดให้บอกว่าผ่านหมด — อย่าหาเรื่องแก้ของที่ถูกอยู่แล้ว

## ด่าน 2 · ถามทีละข้อ

**ถามทีละคำถาม รอคำตอบ แล้วค่อยถามข้อถัดไป** — ยิงรวดเดียวเจ็ดข้อแล้วผู้ใช้ตอบสั้น ๆ
กลับมา คือการเดาที่ห่อด้วยคำถาม

ข้ามข้อไหนได้เมื่อคำตอบก่อนหน้าตอบให้แล้วเท่านั้น แล้วต้องบอกว่าข้ามเพราะอะไร

### 2.0 ตารางนี้อยู่ตรงไหนของสายผู้สร้าง

**ถามก่อนทุกข้อ เพราะมันตัดสินว่า audit block หน้าตายังไง**

ถ้า `user` ยังไม่มีในสคีมา → **บอกผู้ใช้ว่าต้องทำ `user` ก่อน แล้วหยุด**
ทะเบียนที่ทำไปก่อนจะสร้างแถวไม่ได้เลย เพราะ `createdBy` ไม่มีอะไรให้ชี้

ตารางนี้เป็น `user` เอง → `createdBy` / `updatedBy` เป็น **nullable** (ดูบล็อกข้างบน)
ตารางอื่น → **NOT NULL** ทั้งคู่

### 2.1 ตารางนี้เก็บอะไร ใครเป็นคนกรอก

ประโยคเดียวจากปากผู้ใช้ ไม่ใช่จากชื่อตาราง
เอาไปเป็น `///` บนหัว model **และเป็น COMMENT ไทยใน patch.sql**

### 2.2 ฟิลด์ธุรกิจมีอะไรบ้าง

ถามเป็นชื่อไทยที่ผู้ใช้เรียกจริง แล้วผมแปลงเป็น `f.*` เอง
**ถามต่อทุกฟิลด์: บังคับกรอกไหม** — ไม่ถามแล้วเดา `?` เอง คือที่มาของ NOT NULL ที่ลงจริงไม่ได้

ห้ามถามเรื่อง `id` และ audit block — convention ตอบแล้ว ใส่เองเงียบ ๆ

### 2.3 ชื่อห้ามซ้ำไหม

ซ้ำได้ / ห้ามซ้ำทั้งตาราง / ห้ามซ้ำในขอบเขตหนึ่ง (เช่นห้ามซ้ำต่อหมวด)

ห้ามซ้ำ → **partial unique ใน `sql/parts/*.sql`** ไม่ใช่ `@unique` เปล่า
`@unique` เปล่ากับ soft delete = ลบแล้วสร้างชื่อเดิมไม่ได้ตลอดกาล

**ห้ามซ้ำต่อ scope ต้องเขียน index เอง** — ลูป catalogue ทำได้แค่ unique ทั้งตาราง
เช่น ชื่อสายพันธุ์ห้ามซ้ำภายในชนิดสัตว์เดียวกัน — สายพันธุ์ชื่อเดียวกันคนละชนิดสัตว์
ยังอยู่ร่วมกันได้

### 2.4 มี `code` ไหม

**ถามว่า "ในชีวิตจริงมีใครเรียกของนี้ด้วยรหัสไหม"** ไม่ใช่ "จะใส่ code ไหม"
ไม่มีใครเรียก = ไม่ใส่ ให้ `name` เป็น business key แทน (db-conventions กฎเหล็กข้อ 4)

### 2.5 ผู้ใช้จัดลำดับเองไหม

จัดเอง → `sortOrder` **แล้วตารางนี้ห้ามแบ่งหน้า** ต้องมี `PATCH /x/:id/move`
พ่วงมาด้วยเสมอ: ชื่อตารางต้องเข้าลิสต์ CHECK `sort_order` ใน patch.sql

เรียงตามชื่อ/วันที่พอ → ไม่ต้องมี

### 2.6 ลบแล้วเก็บไว้ไหม

business table → soft delete ครบ 6 ช่อง (default)
junction → hard delete, audit แค่ `createdAt` + `createdBy`
log/system → ไม่ลบ, `createdAt` อย่างเดียว

ผู้ใช้ตอบ "ลบทิ้งเลย" → ถามย้ำว่ามีเอกสารอื่นอ้างแถวนี้ไหม มีคนอ้าง = soft เสมอ

**ตารางเซสชันเป็นข้อยกเว้นที่ตั้งใจ** — ลบจริง (hard delete) เท่านั้น
แถวที่มีอยู่แปลว่าเซสชันนั้นใช้ได้ · เหตุผลอยู่ที่ `docs/standards/auth.md`

### 2.7 ผูกกับตารางไหน

ทั้งสองทาง: ตารางนี้ชี้ไปใคร · ใครชี้มาที่ตารางนี้
ทุก relation ถามต่อ: **บังคับมีไหม** และ **ตัวแม่ถูกลบแล้วลูกเป็นยังไง**

**คำถามลบตัวแม่ต้องได้คำตอบก่อนเขียน ห้ามค้าง** — มันเป็นกฎชั้น service ที่บังคับทีหลังก็จริง
แต่ถ้าไม่ถามตอนนี้ก็ไม่มีใครถามอีก แล้วตอนเขียน service จะเดาเอาเอง

ค้างแล้วข้ามไปตารางถัดไปคือทางที่มันหาย — เกิดจริงมาแล้ว: คำถาม "ลบตัวแม่ที่มีลูกได้ไหม"
ค้างไว้ตอนทำตารางหนึ่ง แล้วเด้งไปทำตารางถัดไป ผู้ใช้ต้องทวงเอง
**ก่อนขึ้นตารางใหม่ ไล่ดูก่อนว่าตารางก่อนหน้ามีคำถามค้างไหม**

#### FK บังคับกับ FK ว่างได้ ฐานกันให้คนละแบบ

**Prisma ตั้ง `onDelete` ให้เองตามรูปของ FK — ไม่ได้ถามใคร** และสองแบบนี้ผลต่างกันมาก
ถ้าไม่รู้ จะไปเขียนกฎซ้ำที่ service ทั้งที่ฐานทำให้แล้ว หรือแย่กว่านั้นคือคิดว่าฐานกันให้
ทั้งที่มันปล่อยผ่าน

| รูป FK | Prisma ตั้งให้ | ลบตัวแม่แล้ว |
|---|---|---|
| `BigInt?` ว่างได้ | `SET NULL` | **ลบได้** ลูกกลายเป็น null เงียบ ๆ |
| `BigInt` บังคับ | `RESTRICT` | **ลบไม่ได้** ฐานปฏิเสธเอง |

วัดจริง 2026-08-26 บน Postgres รุ่นเดียวกับที่โปรเจคนี้ใช้ — FK ที่ว่างได้ได้ `SET NULL`
ส่วน FK บังคับได้ `RESTRICT` ทั้งคู่โดยไม่มีใครสั่ง

**"ห้ามลบตัวแม่ที่มีลูก" จึงต้องรู้ว่ากำลังพูดถึง FK แบบไหน**
FK บังคับ → ฐานกันให้แล้ว service แค่แปลง error ให้อ่านรู้เรื่อง
FK ว่างได้ → **ฐานไม่กัน** กฎอยู่ที่ service ที่เดียว ใครรัน SQL ตรง ๆ ข้ามได้

จะเปลี่ยนพฤติกรรมต้องสั่งเอง — `@relation(..., onDelete: Restrict)` บน FK ที่ว่างได้
**เรื่องนี้ผู้ใช้ตัดสิน ไม่ใช่เดา** เพราะมันคือ "ฐานกันให้ด้วยไหม หรือเชื่อ service อย่างเดียว"

## ด่าน 3 · เขียนสองไฟล์ แล้วพิสูจน์ว่าลงจริง

### 3.1 schema.prisma

model + field + relation + `@@index` ของ FK และ `deletedAt`

### 3.2 sql/patch.sql

**ทะเบียนชื่อ-unique ธรรมดา: เติมชื่อตารางเข้า catalogue พอ**

DO block ตัวนั้นทำให้สามอย่างในลูปเดียว — partial unique บน `name` ·
`deleted_pair` CHECK · `COMMENT ON TABLE` ภาษาไทย
**เขียน `CREATE UNIQUE INDEX` เองซ้ำ = index สองตัวทำงานเดียวกัน**

เขียนเองเมื่อ: unique ต่อ scope · unique บน `code` · CHECK เฉพาะทาง · index มีเงื่อนไข
รูปแบบ `CREATE UNIQUE INDEX IF NOT EXISTS <table>_<col>_uniq ON "<table>" (...) WHERE "deleted_at" IS NULL;`

มี `sortOrder` → เติมชื่อตารางเข้าลิสต์ CHECK `sort_order` ด้วย

### 3.3 รัน

```bash
cd apps/api
bun run db:push       # ⚠️ ไม่ใช่ `prisma db push` เปล่า ๆ — มันลบ partial unique ทิ้งเงียบ ๆ
bun run db:generate   # db:push ไม่เรียกให้ · ข้ามแล้ว typecheck ไม่รู้จัก model
bun run typecheck
```

`db:push` เรียก `patch.ts` ให้เอง — ดูบรรทัดสรุป `patch.sql applied — N/N statements`
**N/N ไม่เท่ากันเมื่อไหร่ = มี statement ตก อย่าปล่อยผ่าน**

### 3.4 ตรวจว่าลง DB จริง ไม่ใช่แค่ push ผ่าน

**ห้ามใช้ `psql`** — เครื่อง dev ไม่มี ถามฐานผ่าน Prisma แทน

เขียนสคริปต์ชั่วคราวใน scratchpad แล้วรันด้วย `bun` — เอา `patch.ts` เป็นแบบ
(`PrismaPg` + `PrismaClient` จาก `./prisma/generated/client`) แล้ว query สองอย่าง:

```sql
SELECT column_name, data_type, is_nullable FROM information_schema.columns
  WHERE table_name = '<table>' ORDER BY ordinal_position;

SELECT indexname, indexdef FROM pg_indexes WHERE tablename = '<table>';

-- CHECK และ FK พร้อม onDelete ที่ Prisma ตั้งให้เอง
-- ⚠️ `conrelid::regclass` ต้อง cast `::text` ต่อ — adapter แปลง regclass ไม่ได้ ฟ้อง P2010
SELECT conrelid::regclass::text AS child, conname, pg_get_constraintdef(oid) AS def
  FROM pg_constraint WHERE conrelid = '<table>'::regclass ORDER BY contype, conname;
```

เห็นคอลัมน์ครบ · index ที่ตั้งใจไว้ · **และ `onDelete` ที่ได้จริง** ถึงเรียกว่าจบ

**ตรวจแล้วยังไม่พอ — ต้องลองลบดูด้วย** เขียนสคริปต์สร้างตัวแม่กับตัวลูก แล้วลบตัวแม่จริง ๆ
ทั้ง hard delete และ soft delete แล้วดูว่าลูกเป็นยังไง · `SET NULL` ที่เขียนอยู่ใน constraint
กับที่มันทำจริงเป็นคนละเรื่องกับที่คิดไว้ได้ (วัดจริง 2026-08-26: แถวลูกกลายเป็น null
โดยไม่มีใครห้าม ทั้งที่ผู้ใช้เพิ่งบอกว่าห้ามเกิด)

ลบสคริปต์ทิ้งเมื่อดูเสร็จ — มันเป็นเครื่องมือ ไม่ใช่ของที่ต้องเก็บ

## เสร็จเมื่อ

- [ ] ถามครบ 2.0–2.7 ทีละข้อ ผู้ใช้ตอบเอง ไม่ใช่ผมเดา
- [ ] ผู้ใช้ผ่านสรุปแล้ว (ทั้ง schema และ patch.sql)
- [ ] แตะครบสองไฟล์ หรือบอกได้ว่าทำไมไฟล์ที่สองไม่ต้องแตะ
- [ ] `db:push` + `db:generate` + `typecheck` ผ่าน · patch N/N ครบ
- [ ] query จริงเห็นคอลัมน์และ index ครบ

## ห้าม

- เขียน model ก่อนผู้ใช้ผ่านสรุป
- **ทำตารางอื่นก่อน `user`** — `createdBy` ไม่มีอะไรให้ชี้ สร้างแถวไม่ได้เลย
- **`createdBy = 1` ชี้กลับหาตัวเองบนแถวแรกของ `user`** — sequence ไม่ขยับ แล้ว `db:reset` พัง
- **ลืม `sql/parts/*.sql`** — schema เขียวไม่ได้แปลว่ามีด่านกันซ้ำ
- เขียน `CREATE UNIQUE INDEX` ซ้ำกับที่ลูป catalogue ทำให้แล้ว
- เดาฟิลด์จากชื่อตาราง หรือจากตารางที่คล้ายกันในโปรเจคอื่น
- `prisma db push` / `prisma generate` เปล่า ๆ
- `psql` — ไม่มีในเครื่อง dev
- `@unique` เปล่า ๆ บนตารางที่ soft delete
- ลบ model ที่มี relation ชี้เข้ามา โดยไม่บอกก่อนว่าจะพังกี่ไฟล์
- แตะ service, route หรือหน้าเว็บ — คนละขั้น
