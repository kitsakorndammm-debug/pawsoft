# API Conventions

> สัญญาระหว่าง BE กับ FE · เปลี่ยนที่นี่แปลว่าทุกหน้าจอต้องแก้ตาม

---

## รูปของ response

**ทุก endpoint ตอบด้วยรูปเดียวกัน** FE จึงเช็คที่เดียวได้ ไม่ต้องอ่านโค้ดของแต่ละโมดูล

```jsonc
// สำเร็จ
{ "ok": true, "data": { "id": 12, "name": "สุนัข" } }
{ "ok": true, "data": [ ... ] }

// ปฏิเสธ
{
  "ok": false,
  "error": {
    "code": "DUPLICATE",
    "message": "มีชนิดสัตว์ชื่อนี้อยู่แล้ว",
    "detail": { "field": "name" }
  }
}
```

**`ok` ไม่ได้แทน HTTP status — มันมาคู่กัน** สำเร็จได้ 2xx ปฏิเสธได้ 4xx เสมอ
ใครจะเช็คทางไหนก็ได้ผลตรงกัน · มี `ok` เพราะ FE เขียน `if (!res.ok)` ที่เดียว
อ่านง่ายกว่าไล่ status ทีละช่วง

**`message` เป็นไทย** — เอาไปแสดงบนหน้าจอได้เลย
**`code` เป็นตัวที่โค้ดอ่าน** — ข้อความเปลี่ยนได้ รหัสไม่เปลี่ยน · **เทส assert `code` เท่านั้น**
**`detail` มีเมื่อช่วยให้ทำอะไรต่อได้** — ฟิลด์ไหนซ้ำ ยาวเกินเท่าไหร่

### ข้อความที่ผู้ใช้อ่าน — **FE เป็นคนประกอบ** (ผู้ใช้ตัดสิน 2026-08-26)

BE ส่งของดิบไปให้พอ · FE เอามาเรียงเป็นประโยคเอง เพราะฝั่งนั้นรู้บริบทที่ BE ไม่รู้

| | BE ส่ง | FE แสดง |
|---|---|---|
| สำเร็จ | `{ ok: true, data: { name: "รัชดา" } }` | `สร้างสาขารัชดาสำเร็จ` |
| ปฏิเสธ | `{ code: 'DUPLICATE', detail: { name: "รัชดา" } }` | `มีสาขาชื่อ "รัชดา" อยู่แล้ว` |

**ไม่มี `message` ตอนสำเร็จ** — เพิ่มเมื่อไหร่ ข้อความเดียวกันจะมีสองที่ที่เขียนมัน

**`message` ตอนปฏิเสธเป็นข้อความกลาง ๆ ไม่ประกอบชื่อ** — มีไว้เผื่อ FE ยังไม่ได้ทำ
และเป็นสิ่งที่ log อ่านได้ · FE ที่ทำแล้วใช้ `code` + `detail` ประกอบเอง

**BE ไม่ต้องบอกว่าเป็น entity อะไร** — FE รู้อยู่แล้วว่ากดปุ่มไหน ยิง endpoint ไหน

## error code → HTTP status

| code | status | เมื่อไหร่ |
|---|---|---|
| `INVALID` | 400 | ค่าที่ส่งมาผิดรูปหรือผิดกฎ |
| `UNAUTHORIZED` | 401 | ยังไม่ล็อกอิน หรือเซสชันหมด |
| `FORBIDDEN` | 403 | ล็อกอินแล้วแต่ไม่มีสิทธิ์ |
| `NOT_FOUND` | 404 | ไม่มีแถวนั้น หรือถูกลบไปแล้ว |
| `DUPLICATE` | 409 | ชนกับของที่มีอยู่ |
| `IN_USE` | 409 | ลบไม่ได้เพราะมีของอื่นอ้างอยู่ |

ตารางจริงอยู่ที่ `apps/api/src/kit/app-error.ts` — ที่นี่คือคำอธิบายว่าแต่ละตัวใช้เมื่อไหร่

**error ที่ไม่ใช่ `AppError` = 500** และไม่ส่งรายละเอียดออกไป
ข้อความของ error ที่ไม่ได้ตั้งใจ มักมีชื่อตาราง ชื่อคอลัมน์ หรือ query ติดมาด้วย

## ชนิดบนสาย

| ในฐาน | บนสาย | ทำไม |
|---|---|---|
| `BigInt` (id) | **number** | `JSON.stringify` โยน error ถ้าเจอ BigInt ตรง ๆ · id ไม่ถึง 2^53 |
| `Decimal` (เงิน · จำนวน) | **string** | JSON number เป็น float64 — `0.1 + 0.2` ไม่เท่ากับ `0.3` |
| `DateTime` | **string ISO 8601** | `"2026-08-26T10:00:00.000Z"` |
| `null` | **null** | ไม่ใช่ `undefined` และไม่ตัดคีย์ทิ้ง — FE แยก "ไม่มีค่า" ออกจาก "ไม่มีฟิลด์" ได้ |

**เงินเป็น string ไม่ใช่ความจู้จี้** — บิลค่ารักษาที่รวมยอดผิดไปหนึ่งสตางค์ คือบิลที่ลูกค้า
ทักกลับมาที่เคาน์เตอร์ · ฝั่ง FE คำนวณด้วย string แล้วส่งกลับเป็น string เหมือนกัน

**`BigInt` ห้ามหลุดออกไปทาง JSON** — แปลงที่ชั้น route เสมอ

## เส้นทาง

```
/api/<ทะเบียนพหูพจน์>          pet-species · departments · service-types
```

`kebab-case` · **พหูพจน์** เพราะมันคือคอลเลกชัน

| operation | method + path |
|---|---|
| ดูรายการ | `GET /api/pet-species` |
| ดูรายตัว | `GET /api/pet-species/:id` |
| เพิ่ม | `POST /api/pet-species` |
| แก้ | `PATCH /api/pet-species/:id` |
| ลบ | `DELETE /api/pet-species/:id` |
| ย้ายลำดับ | `PATCH /api/pet-species/:id/move` |

**`PATCH` ไม่ใช่ `PUT`** สำหรับการแก้แถวเดียว — ไม่มี endpoint ไหนที่แทนที่ทั้งแถว

**`PUT` ใช้เมื่อแทนที่ทั้งชุดจริง ๆ** — endpoint ที่รับสถานะสุดท้ายของทั้งกระดานมาแล้ว
diff เอง · ตรงนั้น `PATCH` จะโกหกว่าแก้บางส่วนได้ · ตอนนี้ยังไม่มีเส้นแบบนี้ในระบบ

### ตารางที่ทุกแถวมีเจ้าของ

FK บังคับแปลว่าลิสต์ทั้งตารางไม่มีความหมาย — สายพันธุ์ของสุนัขกับของแมว
เป็นคนละชุด และไม่มีหน้าจอไหนขอดูปนกัน

**ใช้ตัวกรองใน query แล้วบังคับที่ service** ไม่ใช่เส้นทางซ้อน:

```
GET /api/pet-breeds?petSpeciesId=5
```

เส้นทางซ้อน (`/api/pet-species/:id/pet-breeds`) อ่านแล้วชัดกว่าก็จริง
แต่ยืดหยุ่นน้อยกว่า — คิวรีข้ามเจ้าของทำไม่ได้ และ router มีข้อจำกัดเพิ่ม: **ชื่อ
พารามิเตอร์ที่ตำแหน่งเดียวกันของต้นไม้เส้นทางต้องตรงกันทุกเส้น** ไม่งั้น Elysia ปฏิเสธ
ทั้งแอปตอนบูต (วัดแล้ว 2026-08-26 — `:petSpeciesId` ชนกับ `/api/pet-species/:id`
ที่มีอยู่ก่อน แล้วเทสทุกไฟล์พังพร้อมกัน)

**ตัวกรองที่บังคับต้องบังคับที่ service** — `listPetBreeds` รับ `petSpeciesId`
เป็นฟิลด์บังคับใน type ลืมส่งแล้ว typecheck ไม่ผ่าน ซึ่งกันได้ดีกว่า URL ที่อ่านสวย

## `/lookup` — ทะเบียนทุกตัวต้องมี

**บังคับทุกตารางที่มีหน้าจออื่นเลือกค่าจากมัน** (ผู้ใช้ตัดสิน 2026-08-26)

```
GET /api/<ทะเบียน>/lookup        → { ok: true, data: [{ id, name }] }
```

combobox ในหน้าอื่นต้องการแค่ `id` กับ `name` · ให้มันเรียก `GET /api/branches` แล้ว
ได้ทุกคอลัมน์กลับมา แปลว่าหน้าจอหนึ่งจ่ายค่าขนส่งของข้อมูลที่มันไม่ได้ใช้ และวันที่
ทะเบียนนั้นเพิ่มคอลัมน์ ทุกหน้าที่มี combobox ก็หนักขึ้นตามโดยไม่มีใครสังเกต

| | `GET /api/x` | `GET /api/x/lookup` |
|---|---|---|
| ใครใช้ | หน้าจัดการทะเบียนนั้นเอง | combobox ในหน้าอื่น |
| คืนอะไร | ฟิลด์ที่หน้าจัดการต้องใช้ | `id` · `name` เท่านั้น |
| เรียง | ตามที่ผู้ใช้ลากไว้ | เหมือนกัน |
| แถวที่ถูกลบ | ไม่คืน | ไม่คืน |

**คืนเฉพาะแถวที่ยังใช้งานอยู่เสมอ** — combobox คือที่ให้คนเลือกของที่ยังเลือกได้
ส่วนแถวเก่าที่เอกสารเดิมอ้างถึงเป็นคนละคำถาม และตอบด้วยการอ่านเอกสารนั้น ไม่ใช่ด้วย
การให้เลือกใหม่ได้

**ตารางที่มีเจ้าของก็รับตัวกรองเหมือนลิสต์เต็ม** — `GET /api/pet-breeds/lookup?petSpeciesId=5`

**คืน FK เพิ่มได้ เมื่อฟอร์มต้องกรองตัวเลือกเอง** — `/api/positions/lookup` คืน
`departmentId` มาด้วย เพราะฟอร์มพนักงานต้องกรองตำแหน่งตามแผนกที่เลือก **รวมถึงตอนที่
ยังไม่เลือกแผนก** ซึ่งขอผ่าน `?departmentId=` ไม่ได้เพราะมันรับแต่ตัวเลข

นี่ไม่ใช่ใบอนุญาตให้ใส่คอลัมน์ตามใจ · เกณฑ์คือ **หน้าจอกรองตัวเลือกด้วยฟิลด์นั้น**
ไม่ใช่ว่ามันแสดงฟิลด์นั้นด้วย

### `/lookup` ขอแค่ล็อกอิน ไม่ขอสิทธิ์ของเมนู

**ผ่าน auth แล้วเรียกได้เลย ไม่ต้องมี `main:master:read`** (ผู้ใช้ตัดสิน 2026-08-26)

คนที่ลงทะเบียนสัตว์เข้ารักษาต้องเลือกสาขาได้ โดยไม่ต้องมีสิทธิ์เข้าเมนูตั้งค่า · ผูก `/lookup`
ไว้กับสิทธิ์ของเมนูเจ้าของทะเบียนเมื่อไหร่ แปลว่าใครก็ตามที่ต้องเลือกค่าจากทะเบียนนั้น
ต้องได้สิทธิ์ดูหน้าจัดการทะเบียนนั้นไปด้วย — สิทธิ์บานออกไปตามจำนวน combobox

`id` กับ `name` ของทะเบียนที่ยังใช้งานอยู่ ไม่ใช่ความลับ · ส่วนลิสต์เต็มยังเป็นของเมนู
เจ้าของตามเดิม

**วันที่ `GET` ของลิสต์เต็มเริ่มบังคับ `read` ข้อนี้ยังคงอยู่** — `/lookup` ไม่เข้าไปด้วย

ในโค้ดคือ `guardSignedIn` จาก `kit/route-guard` ไม่ใช่ `guardRead`

> **เคยพลาดมาแล้ว 2026-08-26** — ตอนไล่ปิด `GET` ทั้งหมด `/lookup` ทุกเส้นถูกใส่
> `guardRead` ไปด้วย ซึ่งขัดกับกฎข้อนี้ที่เขียนไว้ก่อนหน้า · ไม่มีเทสจับเพราะเทสที่มี
> ยิงแบบไม่ล็อกอิน ซึ่งได้ 401 เหมือนกันทั้งสองแบบ
>
> เทสที่จับได้ต้องเป็นบัญชีที่**ล็อกอินแล้วแต่ไม่มีสิทธิ์** — `/lookup` ต้องได้ 200
> และลิสต์เต็มต้องได้ 403 · อยู่ที่ `test/kit/guard.api.test.ts`

## body ที่ส่งฟิลด์แปลกมา ต้องถูกปฏิเสธ

**Elysia ตัดฟิลด์ที่ไม่ได้ประกาศทิ้งเงียบ ๆ แล้วรัน handler ต่อ**
คนพิมพ์ชื่อฟิลด์ผิดจะได้ 200 กลับไปแล้วเชื่อว่าบันทึกแล้ว ทั้งที่ไม่มีอะไรเปลี่ยน

`additionalProperties: false` **ไม่ช่วยอะไรเลย** (วัดแล้ว 2026-08-26) ทั้ง query และ body

ทุก body schema ต้องปฏิเสธฟิลด์ที่ไม่รู้จักด้วย `400` — **ตรวจใน `transform` เท่านั้น**
เพราะพอถึง handler คีย์แปลกปลอมถูกตัดไปแล้ว และ `request.clone().json()` ก็อ่านไม่ได้
เพราะ body ถูกใช้ไปตอน parse · `transform` ทำงานก่อน validate และเห็น body ดิบครบทุกคีย์

## สิทธิ์

ทุก route ของฝั่งพนักงานประกาศ key ที่ต้องใช้ ตั้งแต่ก่อนมีระบบล็อกอิน

```
<ส่วนของระบบ>:<เมนู>:<read|write>
```

**key แบ่งตามที่ที่ผู้ใช้เห็นบนหน้าจอ ไม่ใช่ตามตาราง** (ผู้ใช้ตัดสิน 2026-08-26)

| ชั้น | คืออะไร | ค่าที่มีตอนนี้ |
|---|---|---|
| ส่วนของระบบ | ที่ที่หน้าจออยู่ | `main` — หน้าบ้านหลังล็อกอิน |
| เมนู | หัวข้อในเมนูนั้น | `master` ตั้งค่า · `hr` บุคคล · `reception` เคาน์เตอร์ · `medical` หมอ · `billing` การเงิน |
| การกระทำ | อ่านหรือเขียน | `read` · `write` (`billing` แยกเป็น `read` · `collect` · `verify`) |

**key ทั้งหมดที่ระบบนี้มีตอนนี้ — ห้ามคิดขึ้นเองนอกลิสต์นี้** (ดู `kit/permissions.ts` เป็นของจริงเสมอ)

```
main:master:read      main:master:write
main:hr:read          main:hr:write
main:reception:read   main:reception:write
main:medical:write
main:billing:read     main:billing:collect     main:billing:verify
```

**ทุกทะเบียนในเมนูตั้งค่าใช้ `main:master:read` / `main:master:write` ร่วมกัน**
ชนิดสัตว์ · สายพันธุ์ · ประเภทบริการ · สาขา — ใครแก้ได้หนึ่งตัว แก้ได้ทั้งเมนู

เพราะสิทธิ์คือสิ่งที่ผู้ดูแลกดให้ในหน้าตั้งค่าสิทธิ์ · key ต่อตารางแปลว่าหน้านั้นมีสวิตช์
เป็นร้อยตัวที่ไม่มีใครไล่กดครบ แล้วคนใหม่จะได้สิทธิ์ไม่ครบโดยไม่มีใครรู้จนกว่าจะกดปุ่มไม่ได้

**`write` คลุม `create` · `update` · `delete` · `move`** — ลากแถวคือการแก้ตาราง
ไม่ใช่สิทธิ์ที่ห้าที่ใครจะได้แยกจากการแก้

**`main:medical:write` ไม่มีคู่ `read`** — คนที่เห็นคิวได้ (`reception:read`) ควรเห็นผล
วินิจฉัยด้วย สิ่งที่ต้องกันคือการ**เขียน** ไม่ใช่การอ่าน (ดู `kit/permissions.ts`)

**`main:billing` แยกเป็นสาม ไม่ใช่คู่ read/write ธรรมดา** — `collect` (เคาน์เตอร์รับเงิน)
กับ `verify` (บัญชียืนยันยอด) เป็นคนละ key โดยตั้งใจ เพื่อให้ maker-checker มีความหมายจริง
คนที่รับเงินเองไม่ควรกดยืนยันยอดของตัวเองได้

**เส้นทางของฝั่งเจ้าของสัตว์ไม่มี permission key** — มันไม่ได้ถามว่า "บทบาทนี้ทำอะไรได้"
แต่ถามว่า "แถวไหนเป็นของบัญชีนี้" ซึ่งตอบด้วยการกรองที่ service ด้วย account id
จากเซสชัน · เหตุผลเต็มอยู่ที่ `auth.md`

key ที่ประกาศไว้จะถูก sync เข้าตาราง `permission` ตอนบูต (ยังไม่มี)
