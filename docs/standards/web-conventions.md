# Web Conventions

> โครงของ `apps/web` · ของชิ้นเดียวกันอยู่ที่เดียวเสมอ
> หน้าตาอยู่ที่ `ui-design.md` · สัญญากับ BE อยู่ที่ `api-conventions.md`

---

## ของแต่ละชิ้นอยู่ที่ไหน

```
apps/web/src/
  app/                หน้าจอ · route ของ Next
    (auth)/           หน้าที่ยังไม่มี session — login, เปลี่ยนรหัสผ่านครั้งแรก
    (main)/           หน้าหลังล็อกอิน — มีเมนู มี sider
  components/
    ui/               ชิ้นส่วนดิบ ไม่รู้จักธุรกิจ — Button, Input, Form
    common/           ชิ้นส่วนที่ประกอบแล้ว ใช้ได้หลายหน้า — AppForm, DataTable
    providers.tsx     provider ทุกตัวรวมกันที่นี่
  features/<โดเมน>/
    api.ts            สัญญากับ endpoint ของโดเมนนั้น
    hooks.ts          query · mutation ที่หน้าจอเรียก
  lib/                ของที่ไม่ผูกกับ React — api-client, routes, utils
  env.ts              env ที่ตรวจแล้ว
  proxy.ts            ด่านหน้าทุก request
```

**หน้าจอไม่เรียก `fetch` และไม่เรียก `api.get` เอง** — เรียก hook ของ `features/`
เส้นทางคือ `หน้าจอ → hooks.ts → api.ts → lib/api-client.ts → BE` ทางเดียว ไม่มีทางลัด

หน้าที่ยิง API เองคือหน้าที่ไม่ได้อยู่ใน cache ของ TanStack Query — แก้ข้อมูลที่หน้าอื่น
แล้วหน้านี้ยังโชว์ของเก่า จนกว่าจะมีคนกด refresh

**ชิ้นส่วนที่ใช้หน้าเดียว วางไว้ข้างหน้านั้น** ไม่ต้องขึ้นมา `components/common/`
ย้ายขึ้นวันที่มีหน้าที่สองเรียกใช้จริง — ไม่ใช่วันที่เดาว่าจะมี

## เกินเจ็ดไฟล์ในโฟลเดอร์เดียว ให้แยกกลุ่ม

**หนึ่งโฟลเดอร์ = หนึ่งเรื่อง** (ผู้ใช้ตัดสิน 2026-08-26)

```
e2e/
  support/     ของที่ spec ใช้ร่วมกัน — scope, auth, shot
  catalogue/   spec ของหน้าทะเบียน — หนึ่งไฟล์ต่อหนึ่งทะเบียน
  screens/     spec ที่ถ่ายภาพหน้าจอ
```

ไม่ใช่

```
e2e/
  scope.ts  auth.ts  branch.spec.ts  department.spec.ts
  position.spec.ts  pet-species.spec.ts  service-type.spec.ts  screenshot.spec.ts
```

ไฟล์กองรวมกันอ่านไม่ออกว่าอะไรเป็นเครื่องมือ อะไรเป็นเทส และคนที่เข้ามาใหม่
ต้องเปิดทีละไฟล์เพื่อรู้ · **ชื่อโฟลเดอร์คือคำอธิบายที่ไม่มีใครต้องเขียน**

### spec เขียนเต็มทุกไฟล์ ไม่มี suite ที่รับ config

**ห้ามมีฟังก์ชันที่รับ config แล้วปล่อยเทสทั้งชุดออกมา** (ผู้ใช้ตัดสิน 2026-08-26)

เหตุผลเดียวกับที่ฝั่งหน้าจอเลิกใช้ kit ที่คืนทั้งหน้า — เพิ่มไฟล์ถูก แต่แก้ไฟล์เดียวแพง:
แก้จุดเดียวกระทบทุกทะเบียนที่เรียกมัน และทะเบียนที่ต่างจากคนอื่นนิดเดียวต้องเพิ่ม flag
ให้ของกลาง จนของกลางกลายเป็นที่รวมของเงื่อนไข

**ยอมให้โค้ดยาวขึ้น** — สิ่งที่ได้คือแต่ละไฟล์แก้ได้โดยไม่ต้องถามว่าใครใช้อยู่อีก
ซึ่งสำคัญกว่าเพราะหน้าจอแต่ละหน้ามีของไม่เท่ากันตั้งแต่ต้น

ที่ใช้ร่วมกันได้คือชิ้นเล็กที่**ไม่รู้ว่ามีทะเบียนอยู่** — `scope` · `auth` · `shot` ·
ลอกไฟล์ข้าง ๆ มาแก้ชื่อคือวิธีที่ตั้งใจ

**แยกตามสิ่งที่มันเป็น ไม่ใช่ตามชนิดของไฟล์** — `catalogue/` ไม่ใช่ `specs/`
เพราะวันที่มี spec ของหน้าเจ้าของสัตว์ มันควรอยู่ `owner/` ไม่ใช่กองรวมใน `specs/`

**เจ็ดไฟล์เป็นเส้นแบ่ง ไม่ใช่กฎเหล็ก** — สามไฟล์ที่เป็นคนละเรื่องกันชัดเจน
แยกได้เลย · สิบไฟล์ที่เป็นเรื่องเดียวกันหมด (เช่น `components/ui/`) ไม่ต้องแยก

## `'use client'` ใส่ให้ต่ำที่สุด

ไฟล์ที่มี `'use client'` ลาก **ทุกอย่างที่มัน import** ไปเป็น client bundle ตามด้วย
ติดที่ layout ครั้งเดียว = ทั้งต้นไม้เป็น client หมด แล้วไม่มีใครสังเกต

ใส่เมื่อไฟล์นั้นใช้ `useState` · `useEffect` · event handler · hook ของ TanStack Query
**ไม่ใส่ที่ layout** — provider แยกไปอยู่ `components/providers.tsx` เพื่อเรื่องนี้โดยเฉพาะ

## path ของหน้าอยู่ใน `lib/routes.ts` ที่เดียว

```ts
router.replace(ROUTE_LOGIN)   // ใช่
router.replace('/login')      // ไม่ใช่
```

path ที่พิมพ์ตรง ๆ คือลิงก์ที่ไม่มีใครรู้ว่าตาย จนกว่าจะมีผู้ใช้กดแล้วเจอ 404
`<Link href>` · `router.push` · `proxy.ts` ใช้ค่าจากไฟล์นี้ทั้งหมด

## api-client แกะ envelope ให้แล้ว

`api.get<T>()` คืน `T` ตรง ๆ ไม่ใช่ `{ ok, data }` · ปฏิเสธเมื่อไหร่โยน `ApiError`

```ts
try {
  const rows = await api.get<PetSpecies[]>('/api/pet-species')
} catch (err) {
  toast.error(toErrorMessage(err))
}
```

| ของ | อ่านยังไง |
|---|---|
| `err.code` | ตัวที่**โค้ด**อ่าน — `DUPLICATE` · `NOT_FOUND` |
| `err.message` | ตัวที่**คน**อ่าน เป็นไทยจาก BE — เอาขึ้น toast ได้เลย |
| `err.httpStatus` | ใช้แยก 401 ออกจากที่เหลือ |

**อย่าเทียบ `err.message` เพื่อตัดสินใจ** ข้อความเปลี่ยนได้ รหัสไม่เปลี่ยน
(กฎเดียวกับที่เทสฝั่ง BE assert `code` — `api-conventions.md`)

**อย่าเขียนข้อความปฏิเสธเองที่ FE** ยกเว้นตอนต่อ API ไม่ติดเลย ซึ่ง api-client
จัดการให้แล้วด้วย `code: 'NETWORK'`

## ข้อความสำเร็จ FE ประกอบเอง จาก payload

**BE ส่งข้อความมาเฉพาะตอนปฏิเสธ** — ตอนสำเร็จมันส่งของกลับมา ไม่ได้ส่งประโยค
คนที่รู้ว่าผู้ใช้เพิ่งทำอะไรคือหน้าจอ ไม่ใช่ endpoint

```ts
const created = await create.mutateAsync({ name: values.name })
toast.success(`เพิ่ม${NOUN} "${created.name}" แล้ว`)   // ใช่ — ชื่อมาจากของที่ BE คืน
toast.success('บันทึกสำเร็จ')                            // ไม่ใช่ — บันทึกอะไร
```

**เอาค่าจากสิ่งที่ BE คืนกลับมา ไม่ใช่จากที่ผู้ใช้พิมพ์** — BE `trim()` ชื่อก่อนบันทึก
ข้อความที่อ้างค่าในฟอร์มจะไม่ตรงกับแถวที่เพิ่งเกิดขึ้นจริง

**ลบเป็นข้อยกเว้น** — endpoint คืน `null` เพราะแถวไม่เหลือแล้ว
ใช้ชื่อที่ถืออยู่ตอนกดยืนยันแทน

**บอกสิ่งที่หน้าจอไม่ได้แสดงให้เห็นอยู่แล้ว** — แถวใหม่โผล่ในตารางแล้วยังเด้ง
"เพิ่มสำเร็จ" ซ้ำ คือการบังหน้าจอเพื่อบอกสิ่งที่มองเห็นอยู่ (`ui-design.md`)
ที่ toast คุ้มค่าคือตอนของหายไปจากจอ (ลบ) หรือกล่องปิดไปแล้ว (บันทึกจาก dialog)

## ชนิดบนสาย รับมาเป็นอะไร ใช้เป็นอันนั้น

| ในฐาน | บนสาย | ที่ FE |
|---|---|---|
| `BigInt` (id) | number | number |
| `Decimal` (เงิน · จำนวน) | string | **string ตลอดทาง** |
| `DateTime` | string ISO | แปลงตอนแสดงเท่านั้น |

**`Number(price)` คือจุดที่ยอดเริ่มเพี้ยน** — `0.1 + 0.2` ไม่เท่ากับ `0.3`
คำนวณเงินด้วย string แล้วส่งกลับเป็น string · บิลค่ารักษาที่ยอดผิดหนึ่งสตางค์
คือบิลที่ลูกค้าทักกลับมาที่เคาน์เตอร์

## TanStack Query — สถานะจาก server อยู่ที่นี่ที่เดียว

**ห้าม `useState` เก็บของที่มาจาก API** ของชิ้นเดียวจะมีสองสำเนาที่ไม่ตรงกัน

| อยากเก็บ | เก็บที่ |
|---|---|
| ข้อมูลจาก API | `useQuery` |
| ฟิลเตอร์ · หน้าที่เปิดอยู่ · คำค้น | URL ผ่าน `nuqs` — refresh แล้วยังอยู่ ส่งลิงก์ให้กันได้ |
| ค่าในฟอร์มที่ยังไม่บันทึก | `react-hook-form` |
| เปิด/ปิด dialog · ซ่อนรหัสผ่าน | `useState` |

**query key เป็น `const` ในไฟล์ `hooks.ts` ของโดเมนนั้น** ไม่พิมพ์ array ซ้ำ —
`['auth','me']` ที่พิมพ์ผิดตัวเดียว คือ invalidate ที่ไม่เกิดอะไรขึ้นเลย และไม่มี error

mutation ที่แก้ข้อมูล ต้อง `invalidateQueries` ของ key ที่เกี่ยวใน `onSuccess` เสมอ

## ฟอร์ม — `AppForm` + `AppFormField` + zod

ทุกฟอร์มใช้คู่นี้ ไม่มีฟอร์มไหนเรียก `useForm` เอง

```tsx
const schema = z.object({ name: z.string().min(1, 'กรอกชื่อ') })

<AppForm schema={schema} defaultValues={{ name: '' }} onSubmit={handleSubmit}>
  {(form) => (
    <AppFormField name="name" label="ชื่อ" required>
      <Input {...form.register('name')} />
    </AppFormField>
  )}
</AppForm>
```

`AppForm` ให้มาแล้ว: validation จาก zod · `method="post"` กันค่าหลุดลง URL ตอนยังไม่ hydrate ·
เลื่อนจอไปหาช่องแรกที่ผิดตอนกดส่ง

**`AppFormField` เป็นตัวเดียวที่วาง label · ดาวแดง · ข้อความ error** — วางเองแปลว่า
แต่ละฟอร์มจัดหน้าไม่เหมือนกัน

**ช่องที่มีอะไรครอบอยู่ ต้องยัด `aria-invalid` ให้ `<input>` เอง** —
`AppFormField` ยัดให้เฉพาะตอน children เป็น element เดียว ๆ (ดูช่องรหัสผ่านหน้า login)

**`disabled` ทุกช่องตอนกำลังส่ง** และปุ่มใช้ `loading` ไม่ใช่ `disabled` เปล่า —
`loading` ทั้งกันกดซ้ำและบอกว่ากำลังทำอยู่ ด้วยความสูงปุ่มเท่าเดิม

---

## ฟอร์มต้องอ่าน BE ก่อน ว่าอะไรบังคับจริง

**`required` ของช่อง มาจาก schema ของ route ไม่ใช่จากความรู้สึก** (ผู้ใช้ตัดสิน 2026-08-26)

เปิด `apps/api/src/modules/<โมดูล>/<โมดูล>.routes.ts` อ่าน body schema ทีละฟิลด์:

| ที่ BE ประกาศ | ที่ฟอร์ม |
|---|---|
| `t.String()` · `t.Number()` | บังคับ · มีดาวแดง |
| `t.Optional(...)` | ไม่บังคับ |
| `t.Union([t.Number(), t.Null()])` | **ไม่บังคับ** — `null` เป็นค่าที่ยอมรับ |

**ช่องที่ BE ยอมให้ว่าง แต่ฟอร์มบังคับ คือฟอร์มที่ปฏิเสธข้อมูลที่ระบบรับได้**
ผู้ใช้กรอกไม่ครบตามที่ตัวเองมี แล้วต้องใส่ค่ามั่วเพื่อให้ผ่าน

ตรงกันข้ามก็แย่พอกัน: ช่องที่ BE บังคับแต่ฟอร์มปล่อยว่าง คือผู้ใช้กดบันทึกแล้วเจอ
ข้อความปฏิเสธ ทั้งที่หน้าจอรู้อยู่ก่อนแล้ว

## ฟอร์มจัดเป็นแถว ไม่ใช่หนึ่งช่องหนึ่งบรรทัด

**ช่องที่เกี่ยวข้องกันอยู่แถวเดียวกัน** (ผู้ใช้ตัดสิน 2026-08-26)

```tsx
{/* ชื่อ · นามสกุล · ชื่อเล่น — สามช่องนี้คือชื่อคนคนเดียว */}
<div className="grid gap-3 sm:grid-cols-3">
  <AppFormField name="firstName" label="ชื่อ" required>…</AppFormField>
  <AppFormField name="lastName" label="นามสกุล" required>…</AppFormField>
  <AppFormField name="nickname" label="ชื่อเล่น">…</AppFormField>
</div>
```

ฟอร์มแปดช่องเรียงลงมาแปดบรรทัดคือกล่องที่ต้องเลื่อน และเป็นการทิ้งพื้นที่แนวนอน
ทั้งหมดไปเปล่า ๆ · ผู้ใช้เห็นทั้งฟอร์มในจอเดียวไม่ได้ จึงไม่รู้ว่าเหลืออีกกี่ช่อง

| จัดคู่กันเมื่อ | ตัวอย่าง |
|---|---|
| เป็นของสิ่งเดียวกัน | ชื่อ · นามสกุล · ชื่อเล่น |
| แม่กับลูก | ชนิดสัตว์ · สายพันธุ์ |
| ค่ากับหน่วย · ช่วงเริ่ม-จบ | น้ำหนัก · หน่วย |

**อย่ายัดคู่กันเพราะมีที่ว่าง** — ช่องที่ไม่เกี่ยวกันวางติดกัน ผู้ใช้จะอ่านว่าเกี่ยวกัน

**สองถึงสามช่องต่อแถว** — สี่ได้เมื่อมีช่องสั้นปนอยู่ (รหัส · ชื่อเล่น) ·
มากกว่านั้นช่องแคบจนอ่านค่าที่กรอกไม่ออก · `sm:grid-cols-N` เสมอ —
จอแคบต้องกลับไปเรียงลงมาทีละช่อง

**ฟอร์มสองช่องก็นับ** — "ชื่อสายพันธุ์ + ชนิดสัตว์" หรือ "ชื่อตำแหน่ง + แผนก"
เรียงลงมาสองบรรทัดคือการทิ้งพื้นที่ไปครึ่งหนึ่งเพื่อดันปุ่มบันทึกให้ไกลมือขึ้น ·
กฎนี้ไม่ได้เริ่มมีผลตอนช่องที่สาม (ผู้ใช้ทวง 2026-08-26 — ตอนนั้นมีสองหน้าที่ยังผิดอยู่)

**ช่องเดียวไม่ต้องทำอะไร** — ทะเบียนที่มีแต่ชื่อใช้ `sm:max-w-md` ตามค่าตั้งต้น

## ช่องกรอกไม่มี placeholder

**ห้ามใส่ `placeholder` ใน `Input` และ `Textarea`** (ผู้ใช้ตัดสิน 2026-08-27)

ป้ายบอกอยู่แล้วว่าช่องนั้นคืออะไร · ข้อความจาง ๆ ในช่องอ่านเหมือนมีค่ากรอกไว้แล้ว
และมันหายไปทันทีที่เริ่มพิมพ์ ซึ่งเป็นตอนที่คนอาจยังต้องการอ่านมันอยู่

คำอธิบายที่จำเป็นจริงเขียนเป็นข้อความใต้ช่อง ไม่ใช่ในช่อง

**ข้อยกเว้นสองอย่าง** — ทั้งคู่ไม่ใช่คำอธิบาย แต่เป็นสถานะของช่อง:

| ที่ | ข้อความ | ทำไม |
|---|---|---|
| `Combobox` ตอนยังไม่ได้เลือก | `เลือกสาขา` | ไม่มีแล้วช่องว่างเปล่า ไม่รู้ว่ากดได้ |
| ช่องค้นหาบนแถบเครื่องมือ | `ค้นหาพนักงาน` | ไม่มีป้ายกำกับ เพราะป้ายจะกินความสูงของแถบ |

**กล่องต้องกว้างพอกับจำนวนคอลัมน์** — จัดสองช่องต่อแถวในกล่อง `sm:max-w-md`
คือช่องที่แคบกว่าเดิมทั้งคู่ · สองคอลัมน์ใช้ `sm:max-w-xl` · สามถึงสี่ใช้ `sm:max-w-2xl`

## ช่องเลือกจากรายการใช้ combobox

**ทุกช่องที่เลือกจากทะเบียนอื่นเป็น combobox ไม่ใช่ `<select>`** (ผู้ใช้ตัดสิน 2026-08-26)

พิมพ์ค้นได้ · มีปุ่มล้างค่าเมื่อไม่บังคับ · แสดงสถานะกำลังโหลด ·
ทะเบียนที่วันนี้มีสิบแถว ปีหน้ามีสองร้อย และ `<select>` ที่เลื่อนหาไม่เจอ
คือช่องที่ผู้ใช้เลิกใช้แล้วโทรมาถาม

### ตัวเลือกมาจาก `/lookup` ไม่ใช่จากลิสต์เต็ม

**combobox ต้องเรียก `GET /api/<ทะเบียน>/lookup`** (ผู้ใช้ตัดสิน 2026-08-26)

`/lookup` ขอแค่ล็อกอิน ไม่ขอสิทธิ์ของเมนูตั้งค่า — คนที่ลงทะเบียนสัตว์เข้ารักษาจึงเลือก
สาขาได้โดยไม่ต้องได้สิทธิ์เข้าหน้าจัดการสาขา · เรียกลิสต์เต็มแทนเมื่อไหร่ ช่องเลือกจะว่างเปล่า
สำหรับคนที่ไม่มีสิทธิ์นั้น ทั้งที่เขาแค่ต้องเลือกชื่อสาขา

และมันคืนแค่ `id` กับ `name` — หน้าที่มี combobox จึงไม่หนักขึ้นตามคอลัมน์ที่ทะเบียน
เจ้าของเพิ่มในอนาคต · รูปเต็มอยู่ที่ `api-conventions.md`

| | ใช้เมื่อ | hook |
|---|---|---|
| `/api/x` | หน้าจัดการทะเบียนนั้นเอง | `useXs(q)` |
| `/api/x/lookup` | combobox ในหน้าอื่น | `useXLookup()` |

**สองอย่างนี้คนละ query key** — ใช้ key เดียวกันแล้ววันหนึ่งจะมีหน้าที่ได้ข้อมูลผิดรูป
จาก cache ของอีกหน้า

### ตัวเลือกเดียว เลือกให้เลย

**มีทางเลือกเดียว = ระบบเลือกให้ · มากกว่านั้น = ผู้ใช้เลือกเอง** (ผู้ใช้ตัดสิน 2026-08-26)

อยู่ที่ `components/common/combobox-field.tsx` ที่เดียว จึงมีผลกับทุกฟอร์มพร้อมกัน

ช่องที่มีทางเลือกเดียวไม่ใช่การเลือก มันคือการกดยืนยันสิ่งที่ระบบรู้คำตอบอยู่แล้ว ·
แต่เดาแทนคนกรอกเมื่อมีหลายตัวเลือก จะมีคนกดบันทึกโดยไม่ได้อ่านว่าเลือกอะไรไป

ใช้กับช่องไม่บังคับด้วย — และค่าที่ผู้ใช้กดล้างทิ้งต้อง **ไม่เด้งกลับมาเอง**
ไม่งั้นปุ่มล้างกลายเป็นปุ่มที่กดแล้วไม่มีอะไรเกิดขึ้น

## `proxy.ts` คือความสะดวก ไม่ใช่ความปลอดภัย

มันเช็คแค่ว่า **มี** cookie ชื่อ `pawsoft_session` ไม่ได้เช็คว่าใช้ได้จริง (ต่อฐานไม่ได้)
ใครก็ตั้ง cookie ชื่อนี้ในเบราว์เซอร์แล้วเดินเข้ามาได้

**ชื่อ cookie ต้องตรงกับ `SESSION_COOKIE` ใน `apps/api/src/kit/actor.ts` เป๊ะ ๆ**
ไม่ตรงแล้วอาการคือล็อกอินสำเร็จ แต่ด่านนี้ยังคิดว่าไม่มีใครล็อกอิน แล้วเด้งกลับ
หน้า login วนไม่จบ โดยไม่มี error ที่ไหนเลย (เกิดจริง 2026-08-26)

**ฝั่งเจ้าของสัตว์ใช้ cookie คนละตัว (`pawsoft_owner`)** — ด่านนี้จึงต้องดูให้ถูกตัว
ตามกลุ่มของหน้า · เช็ค `pawsoft_session` บนหน้าของเจ้าของสัตว์ คือ redirect loop
แบบเดียวกันที่ย้ายไปเกิดอีกฝั่ง · รายละเอียดของสองเซสชันอยู่ที่ `auth.md`

**ตัวจริงคือ BE ที่ตรวจทุก endpoint** · หน้าที่ของ proxy คือกันคนที่ยังไม่ล็อกอิน
ไม่ให้เห็นหน้าเปล่าแล้วงงว่าทำไมไม่มีข้อมูล

**`next` ที่รับมาจาก URL ต้องขึ้นต้นด้วย `/`** ก่อนเอาไป redirect —
ลิงก์ที่ส่งต่อกันมาไม่ควรพาผู้ใช้ที่เพิ่งล็อกอินไปเว็บอื่น

**และต้องเป็น `/` เดี่ยว ไม่ใช่ `//`** — `//evil.com` ขึ้นต้นด้วย `/` ก็จริง
แต่เบราว์เซอร์อ่านเป็น URL เต็มที่ใช้ protocol เดิม · เช็ค `startsWith('/')` เฉย ๆ
จึงปล่อยผ่านทั้งที่ดูเหมือนกันได้

## สิทธิ์ที่ FE คือการซ่อน ไม่ใช่การกัน

ปุ่มที่ผู้ใช้ไม่มีสิทธิ์กด ให้ซ่อน — แต่ **BE ต้องปฏิเสธอยู่ดีถ้ามีคนยิงตรง**
สิทธิ์ที่บังคับแค่ที่ FE คือสิทธิ์ที่ไม่มีอยู่จริง

key ที่ใช้เป็นตัวเดียวกับที่ route ประกาศ (`main:master:read` · `main:master:write` ·
`main:hr:read` · `main:hr:write` · `main:reception:read` · `main:reception:write` ·
`main:medical:write` · `main:billing:read` · `main:billing:collect` · `main:billing:verify`)
รูปเต็มอยู่ที่ `api-conventions.md`

**หน้าฝั่งเจ้าของสัตว์ไม่ใช้ `useCan` เลย** — มันไม่มี key ให้ถาม · สิ่งที่เห็นถูกจำกัด
ด้วยข้อมูลที่ BE คืนมา ซึ่งกรองด้วย account id จากเซสชันไปแล้ว (`auth.md`)

## เทส

| ชั้น | เครื่องมือ | ตอบคำถามว่า |
|---|---|---|
| ตรรกะที่ไม่ต้องมีหน้าจอ | `bun test` | ฟังก์ชันนี้คำนวณถูกไหม |
| หน้าจอหนึ่งหน้า | Testing Library | ผู้ใช้กดแล้วเห็นอะไร |

**เทสยิงผ่านสิ่งที่ผู้ใช้เห็น** — `getByLabelText('ชื่อผู้ใช้')` `getByRole('button', { name: 'เข้าสู่ระบบ' })`

เทสที่ผูกกับ class คือเทสที่แดงตอนเปลี่ยนดีไซน์ ทั้งที่ไม่มีอะไรพัง

**mock ที่ชั้น `api.ts` ของ feature นั้น** ไม่ mock `fetch` — mock `fetch`
แปลว่าเทสรู้จักรูปของ envelope ซึ่งเป็นเรื่องของ `api-client.ts` ไม่ใช่ของหน้าจอ

### เทสแต่ละชั้นมีฐานของตัวเอง

## ภาพหน้าจอ — เทสที่เขียวไม่ได้แปลว่าหน้าตาถูก

`bun run e2e:shot` ถ่ายทุกหน้า ทุกระดับสิทธิ์ ลง `e2e/.artifacts/screens/`

**ค่าเริ่มต้นของ Playwright เก็บภาพเฉพาะตอนพัง** ซึ่งแปลว่าเทสที่เขียวสนิท
ไม่มีใครเคยเห็นว่าหน้าตายังไง · ดีไซน์ที่เพี้ยนผ่านไปได้ทุกครั้ง

**เกิดจริง 2026-08-26** — บัญชีที่อ่านได้อย่างเดียวเห็นปุ่ม "เพิ่ม" กับ grip ลากได้ครบ
เพราะสวิตช์ปิดการตรวจสิทธิ์ (`NEXT_PUBLIC_AUTH_DISABLED`) ค้างอยู่ในไฟล์ env ของ e2e
ทำให้ `useCan` คืน `true` เสมอ · เทสทุกตัวเขียวหมด ภาพเดียวจับได้ทันที

**อย่าสร้างสวิตช์แบบนั้นขึ้นมาอีก** — สวิตช์ที่ปิดการตรวจสิทธิ์ทั้งระบบมีอยู่เพราะ BE
ยังไม่มี `/api/auth` แล้วมันค้างอยู่หลังหมดเหตุที่ต้องใช้ · มันรอให้ใครสักคนตั้งค่า
ผิดที่ผิดเวลา และวันนั้นไม่มีเทสไหนแดง

**ถ่ายทุกบัญชีที่สิทธิ์ต่างกัน** ไม่ใช่แค่ผู้ดูแล — หน้าจอของคนที่แก้ไม่ได้
คือหน้าที่ไม่มีใครเปิดดูจนกว่าจะมีคนโทรมาบอกว่ากดปุ่มไม่ได้

ภาพไม่ถูก commit — มันคือของที่ดูแล้วทิ้ง · การเทียบภาพอัตโนมัติเป็นคนละเรื่อง
และยังไม่มีในระบบนี้
