# ตัวตนและการเข้าใช้งาน

> ระบบนี้มีคนสองพวกที่ไม่เหมือนกันเลย · เอกสารนี้อธิบายว่าทำไมถึงแยกกัน
> และอะไรจะพังถ้ารวมกัน

---

## สองตาราง ไม่ใช่ตารางเดียวที่มีคอลัมน์บอกชนิด

| ตาราง | ใคร | เข้าระบบยังไง | ใครสร้างแถว |
|---|---|---|---|
| `user` | พนักงานหลังบ้าน — สัตวแพทย์ · ผู้ช่วย · เคาน์เตอร์ · ผู้ดูแลระบบ | username + password | ผู้ดูแลเป็นคนสร้างให้ |
| `pet_owner_account` | เจ้าของสัตว์ — ลูกค้าของคลินิก | Google เท่านั้น | ตัวเองตอนล็อกอินครั้งแรก |

**`user` ไม่มีทางสมัครเอง** — ไม่มีหน้า "สมัครสมาชิก" ฝั่งพนักงาน และไม่ควรมี
คนที่จะเข้ามาแก้ข้อมูลคลินิกได้ ต้องมีคนในคลินิกเป็นคนเปิดประตูให้

**`pet_owner_account` ไม่มีคอลัมน์ `passwordHash` เลย** — ไม่ใช่ว่ามีแล้วปล่อยว่างไว้
คอลัมน์ที่ไม่มีอยู่ คือคอลัมน์ที่ไม่มีใครเผลอเขียนรหัสดิบลงไปได้ และไม่มีใครต้องเขียน
โค้ดรีเซ็ตรหัสผ่านให้มัน

### ทำไมไม่ใช้ตารางเดียวแล้วมีคอลัมน์ `kind`

เพราะตารางเดียวแปลว่า **ทุกคิวรีฝั่งหลังบ้านต้องจำให้ได้ว่าต้องใส่ `where kind = 'STAFF'`**
ลืมครั้งเดียวที่ไหนสักแห่ง แล้วเจ้าของสัตว์คนหนึ่งจะไปโผล่ในหน้าจัดการพนักงาน
พร้อมช่องให้กำหนดบทบาท

การลืมแบบนั้นไม่มีอะไรเตือน — โค้ดคอมไพล์ผ่าน เทสที่มีอยู่ก็เขียว เพราะเทสส่วนใหญ่
สร้างแต่พนักงานขึ้นมาทดสอบ · ปัญหาโผล่ตอนมีข้อมูลจริงของทั้งสองพวกอยู่ในฐานเดียวกัน

**สองตารางทำให้ระบบชนิดกันแทนความจำคน** — `listUsers()` คืน `User[]`
มันไปหยิบเจ้าของสัตว์มาไม่ได้ ต่อให้อยากก็ทำไม่ได้

และผลข้างเคียงที่สำคัญพอกัน: **`createdBy` ทั่วทั้งระบบชี้ไปที่ `user.id` ได้แบบไม่กำกวม**
ถ้าเป็นตารางเดียว `createdBy` จะตอบไม่ได้ว่า "แถวนี้ลูกค้าเป็นคนสร้างเองหรือพนักงานสร้างให้"
โดยไม่ต้อง join กลับไปอ่าน `kind` ทุกครั้ง

### `pet_owner_account` ไม่ใช่ `pet_owner`

สองอย่างนี้ชื่อคล้ายกันจนอันตราย จึงต้องแยกให้ชัดตั้งแต่ตอนนี้:

| | `pet_owner_account` | `pet_owner` (ยังไม่มี) |
|---|---|---|
| คืออะไร | **วิธีล็อกอิน** | **คนที่คลินิกรู้จัก** |
| เกิดขึ้นเมื่อ | เจ้าของสัตว์ล็อกอิน Google ครั้งแรก | พนักงานคีย์ข้อมูลลูกค้าเข้าระบบ |
| ใครสร้าง | ตัวเอง | พนักงาน (มี `createdBy`) |
| มีได้โดยไม่มีอีกอัน | ได้ — ล็อกอินแล้วแต่คลินิกยังไม่เคยลงทะเบียนให้ | ได้ — ลูกค้าที่ไม่เคยใช้แอปเลย |

ทั้งคู่ผูกกันทีหลังด้วย **FK ที่ว่างได้** — วันที่พนักงานยืนยันว่า "บัญชี Google นี้
คือคุณสมชายที่มีประวัติอยู่แล้ว" ถึงจะเชื่อมกัน

**ห้ามบังคับให้ต้องมีคู่กันเสมอ** — บังคับเมื่อไหร่ แปลว่าคนที่เพิ่งกดล็อกอิน Google
เข้ามาครั้งแรกจะสร้างบัญชีไม่สำเร็จ เพราะยังไม่มีใครลงทะเบียนเขาไว้
และแปลว่าลูกค้าที่มาแต่หน้าร้านไม่มีที่อยู่ในระบบจนกว่าเขาจะยอมมีบัญชี Google

## สองเซสชัน สอง cookie

| ฝั่ง | cookie | อายุ |
|---|---|---|
| พนักงาน | `pawsoft_session` | 10 ชั่วโมงนับจากล็อกอิน |
| เจ้าของสัตว์ | `pawsoft_owner` | 30 วัน |

**ทั้งคู่เป็น `HttpOnly`** — JavaScript ในหน้าอ่านไม่ได้ · token ที่อ่านได้ด้วยสคริปต์
คือ token ที่หลุดได้ด้วยสคริปต์ของคนอื่นที่หลุดเข้ามาในหน้า

### ทำไมสอง cookie ไม่ใช่ตัวเดียวที่ใช้ร่วมกัน

เพราะเบราว์เซอร์เครื่องเดียวกันต้องถือทั้งสองตัวได้พร้อมกัน

สัตวแพทย์คนหนึ่งเป็นทั้งพนักงานของคลินิกและเจ้าของหมาที่รักษาที่นี่เอง ·
cookie ตัวเดียวแปลว่าเขาล็อกอินเข้าพอร์ทัลเจ้าของสัตว์เมื่อไหร่ เซสชันพนักงานหายทันที
แล้วต้องล็อกอินหลังบ้านใหม่ · สลับไปมาทั้งวัน

ชื่อคนละตัวทำให้ทั้งสองอยู่ร่วมกันได้โดยไม่ต้องมีใครเขียนโค้ดจัดการอะไรเพิ่มเลย

### ที่เก็บใน cookie ไม่ใช่ token ตัวจริง

ทั้งสองฝั่งทำเหมือนกัน:

```
สุ่ม 32 ไบต์ → นั่นคือ token ที่ส่งไปให้เบราว์เซอร์
sha256(token) → นั่นคือสิ่งที่เก็บลงตาราง session
```

**ฐานไม่เคยเก็บ token ดิบ** — ฐานหลุดไปทั้งก้อนเมื่อไหร่ คนที่ได้ไปยังเข้าระบบไม่ได้
เพราะสิ่งที่อยู่ในนั้นเอาไปใส่ cookie แล้วไม่ผ่าน · ตอนตรวจ ระบบ hash ค่าที่รับมา
แล้วค้นด้วยผลลัพธ์

คอลัมน์จึงชื่อ `tokenHash` ไม่ใช่ `token` — ชื่อบอกว่าข้างในเป็นอะไร (`naming.md`)

### เซสชันลบจริงเท่านั้น ไม่มี soft delete

ตาราง session เป็นข้อยกเว้นของกฎ soft delete ทั้งระบบ **โดยตั้งใจ**

**แถวที่มีอยู่ = เซสชันที่ใช้ได้** — ประโยคเดียวจบ ไม่มีเงื่อนไขต่อท้าย

ถ้าใช้ soft delete ทุกที่ที่ตรวจเซสชันจะต้องเขียน `where deletedAt: null` ให้ครบ
และวันที่ลืมสักที่หนึ่ง เซสชันที่ถูกเพิกถอนไปแล้วจะยังใช้ได้ต่อ — ซึ่งเป็นการลืม
ที่ไม่มีใครสังเกตจนกว่าจะสาย

การเพิกถอน (ออกจากระบบ · เปลี่ยนบทบาท · ผู้ดูแลสั่งเตะออก) จึงคือการ `delete` จริง
"ใครเคยล็อกอินเมื่อไหร่" เป็นคนละคำถาม และตอบด้วยตาราง log ไม่ใช่ด้วยแถวเซสชันที่ตายแล้ว

### อายุเซสชัน — คนละเลข เพราะคนละความเสี่ยง

**พนักงาน 10 ชั่วโมง นับจากตอนล็อกอิน ไม่ต่ออายุ**

สิบชั่วโมงคือกะทำงานหนึ่งกะบวกเผื่อ · ไม่ต่ออายุ แปลว่าเครื่องที่เปิดค้างไว้ตอนกลับบ้าน
จะหมดอายุเองในคืนนั้น ไม่ใช่ค้างต่อไปเรื่อย ๆ ตราบใดที่ยังมีคนขยับเมาส์

การต่ออายุอัตโนมัติทุกครั้งที่มีการใช้งาน ฟังดูสะดวก แต่มันแปลว่าเซสชันไม่มีวันหมดอายุ
ตราบใดที่ยังมีใครใช้เครื่องนั้นอยู่ — รวมถึงคนที่ไม่ใช่เจ้าของเครื่อง

**เจ้าของสัตว์ 30 วัน**

คนกลุ่มนี้เข้ามานาน ๆ ครั้ง — ดูผลตรวจ ดูวันนัดครั้งหน้า อาจเดือนละครั้ง ·
บังคับให้ล็อกอินใหม่ทุกวันบนหน้าที่เปิดเดือนละครั้ง คือความยุ่งยากที่ไม่ได้แลกอะไรกลับมา
เพราะบัญชีนั้นเปลี่ยนแปลงอะไรในคลินิกไม่ได้เลย — มันอ่านข้อมูลของตัวเองได้อย่างเดียว

ความเสี่ยงต่างกัน ตัวเลขจึงต่างกัน · ตัวเลขเดียวกันสองฝั่งคือการเลือกให้ฝั่งหนึ่งผิดเสมอ

## นับความพยายามล็อกอินผิด — ฝั่งพนักงานเท่านั้น

ล็อกอินผิดหลายครั้งติดกันแล้วบัญชีถูกล็อก · กฎนี้ใช้กับ `user` ที่เดียว

**ฝั่งเจ้าของสัตว์ไม่มีอะไรให้นับ** — บัญชี Google ไม่มีรหัสผ่านในระบบเรา
ไม่มีช่องให้ใครลองเดา · การเดารหัสเกิดที่หน้าล็อกอินของ Google ซึ่ง Google
เป็นคนกันเอง และกันได้ดีกว่าที่เราจะเขียนได้

การไปนับ "ล็อกอิน Google ไม่สำเร็จ" แล้วล็อกบัญชี จึงเป็นการล็อกคนที่กดยกเลิก
กลางทางหรือเน็ตหลุด ไม่ใช่การล็อกคนร้าย

## HTTPS — Google บังคับ ส่วนหลังบ้านไม่บังคับ

**Google OAuth ยอมรับ `http://localhost` และ `http://127.0.0.1` เป็นข้อยกเว้นที่เขียนไว้
ในเอกสารของเขาเอง** — เครื่อง dev จึงไม่ต้องตั้ง TLS อะไรทั้งนั้น

**ทุก host อื่นต้องเป็น `https://`** ไม่มีข้อยกเว้น · IP ในวง LAN อย่าง
`http://192.168.1.50:3200` **Google ปฏิเสธ** ลงทะเบียนเป็น redirect URI ไม่ได้ตั้งแต่ต้น
ไม่ใช่ลงได้แล้วค่อยพังตอนใช้

ผลในทางปฏิบัติ: **ฝั่งเจ้าของสัตว์ทดสอบข้ามเครื่องในวง LAN ไม่ได้** จนกว่าจะมีโดเมนจริง
กับใบรับรอง · ฝั่งพนักงานไม่มีข้อจำกัดนี้ เพราะมันไม่ได้คุยกับ Google — เปิดจากมือถือ
ในวงเดียวกันด้วย http ได้ตามปกติ

**วันที่ขึ้น TLS จริง สิ่งที่ต้องแก้คือ `secure: true` บน cookie ทั้งสองตัว**
อยู่ที่ `apps/api/src/kit/actor.ts` (ตัวที่ตั้งค่า cookie ทั้งสอง) — บรรทัดเดียว ไม่ใช่
การรื้อ · เขียนไว้ตรงนี้เพราะของแบบนี้มักหาไม่เจอตอนที่ต้องการ

## สิทธิ์เป็นเรื่องของพนักงานเท่านั้น

**`pet_owner_account` ไม่ถือ permission key แม้แต่ตัวเดียว** และจะไม่มีวันถือ

สิ่งที่เจ้าของสัตว์เห็น ถูกจำกัดด้วย **การกรองด้วย account id จากเซสชัน**
ที่ชั้น service ของทุก endpoint ฝั่งนั้น — ไม่ใช่ด้วยการเช็ค key

### ทำไม key เป็นเครื่องมือผิดข้อสำหรับเรื่องนี้

permission key ตอบคำถามว่า **"บทบาทนี้ทำอะไรได้บ้าง"** — คำตอบเหมือนกันสำหรับ
ทุกคนที่ถือบทบาทเดียวกัน นั่นคือจุดที่มันมีประโยชน์

คำถามของฝั่งเจ้าของสัตว์คือ **"แถวไหนเป็นของคุณ"** — คำตอบต่างกันสำหรับทุกคน
ต่อให้ทุกคนมีสิทธิ์เท่ากันเป๊ะ

สมมติมี key ชื่อ `owner:pet:read` ขึ้นมาจริง ๆ มันก็ตอบได้แค่ว่า "คนนี้ดูสัตว์ได้"
ซึ่งเป็นจริงกับเจ้าของสัตว์ทุกคนในระบบ — แล้วคำถามที่เหลือ ("สัตว์ตัวไหน")
ก็ยังต้องไปตอบด้วยการกรองที่ service อยู่ดี

**key ตัวนั้นจึงไม่ได้กันอะไรเลย นอกจากทำให้คนอ่านโค้ดคิดว่ามันกัน** — ซึ่งแย่กว่า
ไม่มีมัน เพราะคนที่เห็น guard อยู่ตรงหัว route อาจไม่ไล่ต่อว่าข้างในกรองครบไหม

**กฎเหล็ก: ทุก service ฝั่งเจ้าของสัตว์รับ account id เป็นพารามิเตอร์บังคับ**
ไม่ใช่ค่าที่ว่างได้ · ลืมส่งแล้ว typecheck ไม่ผ่าน ซึ่งเป็นด่านที่ดีกว่าการจำให้ได้ว่า
ต้องใส่ `where` ตัวไหน

รูปเต็มของ permission key ฝั่งพนักงานอยู่ที่ `api-conventions.md`
