> สิ่งที่ผู้ใช้เห็น · เปลี่ยนที่นี่แปลว่าทุกหน้าจอเปลี่ยนตาม

## ระบบนี้ไม่มีสีที่พิมพ์ลงในคอมโพเนนต์

**เรียกโทเคน ไม่เรียกสี** — `bg-background` `text-muted-foreground` `border-border`
ไม่ใช่ `bg-white` `text-gray-500` หรือรหัสสีตรง ๆ

โทเคนทุกตัวอยู่ที่ `apps/web/src/app/globals.css` ที่เดียว

`bg-white` ที่พิมพ์ลงในหน้าจอหนึ่งหน้า คือหน้าที่เดียวที่ยังขาวตอนคนอื่นเปลี่ยนธีม
และเป็นหน้าที่ `grep` หาไม่เจอเพราะไม่มีใครจำได้ว่าเขียนไว้ตรงไหน

| อยากได้ | ใช้ |
|---|---|
| พื้นหลังหน้า | `bg-background` · ตัวอักษร `text-foreground` — **เทาอ่อนมาก ไม่ใช่ขาวล้วน** (`oklch(0.985 0 0)`) ให้การ์ดขาวลอยเด่นแยกจากพื้น |
| พื้นการ์ด · dialog | `bg-card` · `bg-popover` — ขาวล้วน |
| ปุ่มหลัก · โฟกัส · ลิงก์ | `bg-primary` · `ring-ring` |
| ตัวอักษรรอง · คำอธิบาย | `text-muted-foreground` |
| พื้นอ่อน · แถบ hover | `bg-muted` · `bg-accent` |
| ลบ · error · กรอบแดง | `text-destructive` · `bg-destructive` |
| เส้นขอบ · เส้นคั่น | `border-border` · ช่องกรอก `border-input` |

**ข้อยกเว้นเดียว: สีที่แปลว่าสถานะเฉพาะเรื่อง** — เขียวว่าผ่าน ส้มว่ารอ
พวกนี้ประกาศเป็น variant ในคอมโพเนนต์ (`success` · `warning` ของ `Button`)
ไม่ใช่ `className="bg-green-500"` ที่หน้าจอ · สีของ "ผ่าน" ต้องเป็นเขียวเดียวกันทั้งระบบ

**`className="border ... bg-card ..."` ได้เงายกตัวให้ฟรี** — กฎ global ใน `globals.css`
(`@layer base`) จับคู่คลาส `border` + `bg-card` ที่เขียนอยู่แล้วทั่วระบบ (การ์ดในตารางจอง ·
แถวประวัติ · ผลค้น ฯลฯ) แล้วใส่ `box-shadow` ให้อัตโนมัติ — **เขียนสองคลาสนี้คู่กันพอ**
ไม่ต้องเติม `shadow-*` เอง และ `DataTable`s wrapper ก็ใช้ `bg-card` เพื่อรับเงานี้เหมือนกัน

## สีแบรนด์คือสีของสิ่งที่ต้องกด ไม่ใช่สีตกแต่ง

`--primary` เป็นสีเดียวของแบรนด์ · มันอยู่บนของที่ผู้ใช้ต้องกด — ปุ่มหลัก แถบโฟกัส
ลิงก์ · **ที่เหลือเป็นเทา**

หน้าจอที่มีสีแบรนด์หลายจุด คือหน้าจอที่ผู้ใช้ไม่รู้ว่าต้องกดตรงไหน

**`--destructive` เป็นคนละตัวกับ `--primary`** ตั้งใจให้ต่างกัน — ปุ่มลบต้องไม่หน้าตา
เหมือนปุ่มหลัก แม้จะเป็นโทนใกล้กัน

### สีของ Paw Soft คือ **ฟ้า** — โครงยกมาจาก PMK ทั้งชุด (ผู้ใช้ตัดสิน 2026-08-31)

**เปลี่ยนอย่างเดียวคือสีแบรนด์: แดง PMK → ฟ้า** · ที่เหลือเหมือนเดิมทุกค่า —
เทากลาง รูปทรง scrollbar ระยะขอบ (พื้นหลังหน้าเทาอ่อนขึ้นทีหลัง — ดูหัวข้อ
"พื้นหลังหน้า" ด้านบน)

ยกมาทั้งชุดเพราะมันผ่านการใช้งานจริงมาแล้ว · แก้ทีละค่าตามความรู้สึกคือการทิ้ง
สิ่งที่พิสูจน์แล้วไปโดยไม่ได้อะไรกลับมา

| | PMK | Paw Soft |
|---|---|---|
| `--primary` | `oklch(0.54 0.22 25)` แดง `#d00021` | `oklch(0.55 0.17 242.6)` ฟ้า `#0078cb` |
| `--primary-foreground` | ขาว (5.66:1) | ขาว — **4.62:1 ผ่าน AA** |
| `--primary-strong` | (ไม่มี) | **ฟ้าเข้ม `#006fab` — สำหรับตัวหนังสือ** |
| ที่เหลือทั้งหมด | เทากลาง | **เหมือนเดิมทุกค่า** |

### ประวัติสีปุ่มหลัก — ไล่แก้ 3 รอบกว่าจะผ่านมาตรฐานจริง

**ตัวหนังสือขาวบนปุ่ม `--primary` ต้องได้อย่างน้อย `4.5:1` (WCAG AA)** — ไล่ไปตาม
เวลาจริง เพราะแต่ละรอบมีบทเรียนของมันเอง:

| วันที่ | `--primary` | เลขจริงที่วัด | หมายเหตุ |
|---|---|---|---|
| 2026-08-31 | `oklch(0.705 0.163 242.6)` `#1ca9fc` | `2.58:1` | ฟ้าสดใสตามที่ผู้ใช้เลือก **ตกมาตรฐานโดยตั้งใจ** — เห็นตัวเลขแล้วยังเลือกใช้ |
| 2026-09-20 (รอบ 1) | `oklch(0.62 0.17 242.6)` `#008ee3` | `3.51:1` | เข้มขึ้นแต่ยังไม่ผ่าน — **คอมเมนต์ตอนนั้นเขียนผิดว่าได้ `4.52:1`** เพราะกะเอาจาก oklch lightness ตรง ๆ โดยไม่ได้แปลงเป็น sRGB จริงแล้ววัด |
| 2026-09-22 (รอบ 2) | `oklch(0.55 0.17 242.6)` `#0078cb` | **`4.62:1` ผ่าน** | ค่าปัจจุบัน — วัดจาก hex จริงผ่านสูตร WCAG ตรง ๆ ไม่ประมาณจาก oklch |

**บทเรียน: ห้ามเดาค่า contrast จาก lightness ของ oklch ตรง ๆ** ต้องแปลงเป็น sRGB
(ผ่าน `oklch()` → linear RGB → gamma) แล้วคำนวณ relative luminance ตามสูตร WCAG จริง
ถึงจะเชื่อได้ · เขียนคอมเมนต์คาดเดาไว้ก่อนวัดจริง คือที่มาของรอบ 1 ที่ตัวเลขผิด

### `--primary-strong` — ฟ้าเข้มสำหรับตัวหนังสือ

คนละเรื่องกับข้างบน และตัวนี้**ผ่านมาตรฐานมาตั้งแต่ต้น ไม่ต้องไล่แก้** · ฟ้าสดใส
ใช้เป็นตัวหนังสือบนพื้นขาวไม่ได้ (contrast ต่ำเกินไปไม่ว่าจะรอบไหน) จึงมีฟ้าเข้มของ
hue เดียวกัน (`#006fab` · `5.44:1`) แยกไว้ใช้กับลิงก์ ไอคอน และวงโฟกัสต่างหาก

```css
@layer utilities {
  .text-primary { color: var(--primary-strong); }
  .border-primary { border-color: var(--primary-strong); }
}
```

**คลาส `text-primary` ถูกเปลี่ยนให้ชี้ตัวเข้มเลย** เพราะคอมโพเนนต์ที่ยกมาจาก PMK
เขียนมันไว้สิบกว่าที่ (ไอคอนค้นหา · แถวที่เลือกใน combobox · หัวคอลัมน์ที่กำลังเรียง ·
แท็บที่ active) · ตอนแบรนด์เป็นแดงเข้มมันอ่านออกหมด พอเปลี่ยนเป็นฟ้าสว่างก็จางไป
พร้อมกันทั้งหมด · ไล่แก้ทีละที่แปลว่าจะพลาดที่ใดที่หนึ่งแน่ ๆ

`bg-primary` ยังเป็นสีเดียวกับ `--primary` เสมอ (ตอนนี้คือ `#0078cb`) — พื้นปุ่มกับพื้นแถบ
คือที่ของมัน

> **วัดครบ 10/10 ผ่าน AA** (2026-08-31) — ตัวอักษรปกติและตัวรอง · `text-primary` ทั้งบนขาว
> และบนเทาอ่อน · ปุ่มลบ/บันทึก/เตือน · วงโฟกัส **ไม่รวมตัวอักษรบนปุ่มหลัก** ซึ่งตอนนั้นยัง
> ตกมาตรฐานอยู่ (ดู "ประวัติสีปุ่มหลัก" ด้านบน) — ผ่านจริงทั้ง 11 รายการเมื่อ 2026-09-22

**`--muted` กับ `--accent` เป็นเทา ไม่ใช่ฟ้า** — ตามโครงเดิมของ PMK (ผู้ใช้ตัดสิน
2026-08-31) · ฟ้าอยู่ที่ `--primary` ที่เดียว ซึ่งเป็นเหตุผลที่หน้าจอบอกได้ว่าต้องกด
ตรงไหน · พื้นอ่อนที่มีสีจะแย่งสายตากับปุ่ม แล้วสีแบรนด์ก็เลิกทำหน้าที่ของมัน

### `dark:` ผูกกับคลาส `.dark` ไม่ใช่กับเครื่องของผู้ใช้

```css
@custom-variant dark (&:is(.dark *));
```

**บรรทัดนี้ต้องมี และห้ามลบ** · ค่าตั้งต้นของ Tailwind คือ
`@media (prefers-color-scheme: dark)` — คอมโพเนนต์ที่ยกมาจาก PMK มีคลาส `dark:`
อยู่เต็มไปหมด (`dark:bg-input/30` ที่ `input.tsx` เป็นต้น)

ไม่ประกาศบรรทัดนี้ คลาสพวกนั้นทำงานทันทีบนเครื่องที่ตั้งเป็นโหมดมืด แล้ว
**ช่องกรอกกลายเป็นพื้นเทาบนหน้าจอที่เป็นขาว** โดยไม่มีอะไรในโค้ดของเราบอกว่าทำไม
(เจอเมื่อ 2026-08-31 — หาอยู่นานเพราะ `globals.css` ของเราไม่มี `prefers-color-scheme`
สักตัว มันมาจากค่าตั้งต้นของ Tailwind ล้วน ๆ)

ระบบนี้ไม่มีใครใส่คลาส `.dark` ให้ `<html>` · เงื่อนไขจึงเป็นเท็จเสมอ และคลาส `dark:`
ทั้งหมดถูกปิดตายไปพร้อมกัน ซึ่งเป็นสิ่งที่ต้องการ

### ไม่มีโหมดมืด และตั้งใจไม่มี

PMK มี `.dark` แต่ **ที่นี่ถอดออก** (ผู้ใช้ตัดสิน 2026-08-31)

เคยมี `@media (prefers-color-scheme: dark)` อยู่ · ผลคือคนที่ตั้งเครื่องเป็นโหมดมืด
ไม่เคยเห็นสีที่ออกแบบไว้เลยสักครั้ง — เปิดมาเจอพื้นดำ ทั้งที่สิ่งที่สั่งคือพื้นขาว
และไม่มีทางรู้ว่าพื้นขาวมีอยู่จริงถ้าไม่ไปสลับธีมของเครื่อง

`:root { color-scheme: light }` บอกเบราว์เซอร์ด้วยว่าอย่าไปกลับสีของ scrollbar หรือ
control ให้เอง — ไม่บอก เบราว์เซอร์จะวาดช่องกรอกเป็นสีเข้มบนหน้าจอที่เป็นขาว

วันที่อยากได้โหมดมืดจริง ๆ ให้เพิ่มเป็น**สวิตช์ที่ผู้ใช้กดเอง** ไม่ใช่ให้มันเปลี่ยน
ตามเครื่องโดยที่ไม่มีใครสั่ง · `@custom-variant dark` ที่มีอยู่แล้วรองรับทางนั้นพอดี

### สถานะที่ PMK ไม่มี

`--success` (เขียว บันทึก) กับ `--warning` (เหลือง รอ) เป็นของเพิ่มที่นี่ ·
ทั้งคู่วัดแล้วผ่าน AA กับตัวอักษรขาว — `--warning` ต้องเข้มกว่าที่ตาคาด
(`L 0.62` ตกที่ 3.72:1 · ขาวบนเหลืองสว่างอ่านไม่ออก)

**`--input` เข้มกว่า `--border` โดยตั้งใจ** — เส้นคั่นเป็นของตกแต่ง จางได้
แต่ขอบช่องกรอกคือสิ่งที่บอกว่า "ตรงนี้พิมพ์ได้" ซึ่งต้องมองเห็น · WCAG บังคับ 3:1
กับขอบของ control และเส้นจาง ๆ ที่สวยดีบนจอเราจะหายไปเลยบนจอที่ปรับความสว่างต่ำ

**เปลี่ยนค่าพวกนี้ต้องวัด contrast ใหม่ทั้งชุด** ไม่ใช่แค่ดูว่าสวยขึ้นไหม ·
`--primary` ที่อ่อนลงนิดเดียวทำให้ตัวอักษรบนปุ่มตกมาตรฐานได้ทันที

## ฟอนต์เดียว: Sarabun

มาทาง `next/font/google` ที่ root layout **ไม่ใช่ `<link>` ไป Google**
ฟอนต์ถูกเสิร์ฟจากเครื่องเรา — หน้าจอไม่กระพริบเป็นฟอนต์ระบบก่อนหนึ่งจังหวะ
และไม่พังตอนเครื่องผู้ใช้ออกเน็ตนอกไม่ได้

น้ำหนักที่มี `300 400 500 600 700` · **ไม่มี italic** ภาษาไทยเอียงแล้วอ่านยากขึ้น ไม่ได้เน้นขึ้น

| ที่ | ขนาด |
|---|---|
| เนื้อหาทั่วไป · ช่องกรอก · ปุ่ม | `text-sm` |
| หัวข้อหน้า | `text-lg` · `font-semibold` |
| คำอธิบายใต้ช่อง · footer · ข้อความ error | `text-xs` |

**ตัวหนาใช้ถึง `font-semibold`** — `font-bold` ในภาษาไทยกลายเป็นก้อนดำ

## ระยะห่าง — คูณสี่เสมอ

`gap-2` `p-4` `space-y-6` · ไม่ใช่ `gap-[7px]`

ค่ากลาง ๆ ที่กะเอาเองทำให้แต่ละหน้าห่างไม่เท่ากัน แล้วไม่มีใครรู้ว่าอันไหนตั้งใจ

| ระหว่าง | ระยะ |
|---|---|
| ไอคอนกับตัวอักษรในปุ่ม | `gap-1.5` |
| ช่องกรอกกับ label | `gap-2` |
| ช่องกรอกแต่ละช่องในฟอร์ม | `space-y-4` |
| กลุ่มเนื้อหาในหน้า | `space-y-6` |
| ขอบในของการ์ด · dialog | `p-4` ถึง `p-8` |

## ตารางแน่นไว้ก่อน — พื้นที่จอมีจำกัด

ทะเบียนหนึ่งตัวมีได้เป็นร้อยแถว และผู้ใช้มาที่นี่เพื่อ**กวาดตาหา** ไม่ใช่มาอ่านทีละแถว
แถวที่สูงเกินจำเป็นแปลว่าต้องเลื่อนจอเพื่อดูของที่ควรอยู่ในหน้าจอเดียว

| ของ | ค่า |
|---|---|
| แถวในตาราง | `px-2 py-1.5` — ไม่ใช่ `p-4` |
| ระยะระหว่างคอลัมน์ | `gap-2` |
| ปุ่มไอคอนในแถว | `size="icon-sm"` · ไอคอน `size-3.5` |
| ระยะระหว่างส่วนของหน้า | `gap-3` — ไม่ใช่ `gap-6` |

**ปุ่มในแถวเห็นตลอด ไม่ต้องชี้ก่อน** (ผู้ใช้ตัดสิน 2026-08-26)

ซ่อนจนกว่าจะ hover แปลว่าคนที่ใช้จอสัมผัสหาปุ่มไม่เจอเลย และคนที่ใช้เมาส์
ต้องกวาดหาว่าแถวนี้กดอะไรได้บ้าง · ปุ่มเป็น `ghost` สีจาง จึงไม่แย่งสายตากับข้อมูล
ในแถวอยู่แล้ว

**ปุ่มไอคอนต้องมีคำอธิบายตอนชี้** (ผู้ใช้ตัดสิน 2026-08-26)

ไอคอนอย่างเดียวคือการเดา — ดินสอกับตาพอเดาได้ แต่คนที่ไม่เคยใช้ระบบนี้
ไม่รู้ว่าถังขยะลบทันทีหรือถามก่อน · และไอคอนคนมีกากบาทกับคนมีถูก แยกออกยาก
ถ้าไม่มีคำกำกับ

**ใช้ข้อความเดียวกับ `aria-label`** — คนที่ใช้โปรแกรมอ่านหน้าจอกับคนที่ชี้เมาส์
ควรได้ยินเรื่องเดียวกัน · และข้อความนั้นควรบอกทั้งการกระทำและสิ่งที่จะโดน
(`แก้ไข สมชาย ใจดี` ไม่ใช่ `แก้ไข`)

`TooltipProvider` อยู่ที่ `components/providers.tsx` หน่วง 300ms — ขึ้นทันที
จะกระพริบตามเมาส์ที่กวาดผ่าน และบังของที่ผู้ใช้กำลังจะกด

**ที่ว่างที่จองไว้ ต้องจองเท่าเดิมเสมอ** — ที่ของ grip ตอนลากไม่ได้ ยังต้องกว้างเท่าเดิม
ไม่งั้นชื่อขยับซ้ายขวาตอนสลับโหมด

**ไม่ต้องมีหัวข้อหน้า ถ้าเมนูบอกอยู่แล้ว** (ผู้ใช้ตัดสิน 2026-08-26) —
รายการที่ active ใน sider บอกว่ากำลังอยู่หน้าไหน · `<h1>` ที่เขียนคำเดียวกันซ้ำ
กินความสูงไปหนึ่งบรรทัดเพื่อบอกสิ่งที่บอกไปแล้ว

หัวข้อมีเมื่อมันบอกอะไรที่เมนูบอกไม่ได้ — ชื่อของแถวที่กำลังเปิดอยู่ เช่น
หน้ารายละเอียดสัตว์ที่ต้องขึ้นชื่อสัตว์ตัวนั้น

### แถบบนของหน้ารายการ — ค้นซ้าย ปุ่มขวา

```
[ ค้นหา… ]                                        [ + เพิ่ม ]
```

**ช่องค้นชิดซ้าย** (ผู้ใช้ตัดสิน 2026-08-26) — ตาเริ่มอ่านจากซ้าย และการค้นคือ
สิ่งที่ผู้ใช้ทำบ่อยที่สุดในหน้ารายการ

**ปุ่มที่สร้างของใหม่ไปสุดขวา** — แยกของที่กดเพื่อ**หา** ออกจากของที่กดแล้ว**เกิดแถวใหม่**
วางติดกันคือปุ่มสร้างที่โดนกดพลาดตอนตั้งใจจะค้น

## สิทธิ์เปลี่ยนหน้าตา ไม่ใช่แค่ปิดปุ่ม

**ปุ่มที่กดไม่ได้ ไม่ต้องมี** — ปุ่มจางที่กดแล้วไม่เกิดอะไร คือผู้ใช้ที่ลองกดซ้ำ
แล้วสรุปเองว่าระบบพัง

| มีสิทธิ์เขียน | ไม่มี |
|---|---|
| ปุ่มเพิ่ม | ไม่มีปุ่ม |
| ปุ่มแก้ไข (ดินสอ) | **ปุ่มดู (ตา)** — ที่เดิม ขนาดเดิม |
| ปุ่มลบ | ไม่มีปุ่ม |
| ลากจัดลำดับได้ | grip หายไป แต่ที่ยังจองไว้ |

**ดู กับ แก้ไข เป็นปุ่มเดียวสลับกัน ไม่ใช่สองปุ่ม** — คนอ่านอย่างเดียวยังต้องเปิดดู
ชื่อเต็มได้เมื่อมันยาวเกินความกว้างคอลัมน์ · สองปุ่มที่ปุ่มหนึ่งกดไม่ได้ กินที่เปล่า

**กล่องเดิม โหมด `view`** ไม่ใช่กล่องที่สาม — ฟอร์มเดียวกันวางสามที่ วันหนึ่งจะไม่ตรงกัน
`readOnly` ปิดการแก้ · ปุ่มบันทึกหายไป · ปุ่มยกเลิกเปลี่ยนคำเป็น "ปิด"

## ความสูงของของที่กดได้

`Input` และ `Button` สูง `h-8` เท่ากัน — วางเรียงกันบนแถวเดียวแล้วขอบบนล่างตรงกัน
ของที่สูงไม่เท่ากันหนึ่งพิกเซล มองไม่ออกว่าผิด แต่รู้สึกได้ว่าหน้าจอไม่เรียบร้อย

| size | สูง | ใช้เมื่อ |
|---|---|---|
| `sm` | `h-7` | ในแถวของตาราง |
| `default` | `h-8` | ทั่วไป |
| `lg` | `h-9` | ปุ่มหลักของหน้า |

### สีของปุ่ม บอกว่ากดแล้วเกิดอะไร

**ปุ่มที่สร้างหรือบันทึกข้อมูลเป็นเขียว** `variant="success"` (ผู้ใช้ตัดสิน 2026-08-26)

| ปุ่ม | variant | สี |
|---|---|---|
| เพิ่ม · สร้าง · บันทึก · ยืนยันที่เขียนข้อมูล | `success` | เขียว |
| ลบ (ปุ่มในหน้า ที่เปิดกล่องยืนยัน) | `destructiveSolid` | แดงเข้ม |
| เดินหน้าต่อ ที่ไม่ได้เขียนข้อมูล — เข้าสู่ระบบ · ถัดไป | `default` | สีแบรนด์ |
| ยกเลิก · ปิด | `outline` | ขาว มีขอบ |
| ปุ่มในแถวตาราง | `ghost` | ใส |

**เขียวสงวนไว้ให้การเขียนข้อมูลเท่านั้น** — ปุ่มที่ทำให้เกิดแถวใหม่หรือแก้แถวเดิม
ผู้ใช้จึงกวาดตาหาปุ่มเขียวได้ทันทีว่า "อันนี้คือปุ่มที่บันทึก"

**ยกเว้นในกล่องยืนยัน — ปุ่มยืนยันเขียวเสมอ รวมปุ่มลบ** (ผู้ใช้ตัดสิน 2026-08-27)

ในกล่องยืนยัน สีไม่ได้ทำหน้าที่บอกว่ากำลังจะเกิดอะไร เพราะหัวข้อกับคำอธิบายบอกไปแล้ว
และคนมาถึงตรงนั้นเพราะตั้งใจกดปุ่มแดงมาก่อน · ปุ่มเขียวหมายถึง "ยืนยันสิ่งที่เลือกไว้"
เหมือนกันทุกกล่อง ไม่ต้องอ่านสีใหม่ทุกครั้ง

`ConfirmDialog` จึงไม่มี prop ให้เปลี่ยนสีปุ่ม — prop ที่รับไว้แต่ไม่มีผลคือคำสัญญา
ที่หน้าจอไม่ได้ทำตาม

**เข้าสู่ระบบไม่ใช่การสร้าง** จึงเป็นสีแบรนด์ตามเดิม — มันคือการเดินเข้า ไม่ได้เขียนอะไร

**ปุ่มที่มีสีพื้น (`default` · `success` · `destructiveSolid` · `warning` · `continueAction`)
มีเงาบางและยกตัวนิดหน่อยตอนชี้เมาส์** (`shadow-sm` → `hover:shadow-md` +
`hover:-translate-y-0.5`, ผู้ใช้ตัดสิน 2026-09-20) ให้รู้สึกจับต้องได้ · **`outline`/`ghost`/
`secondary` ไม่มีเงา** เพราะเป็นปุ่มรอง สีจางอยู่แล้ว เพิ่มเงาจะแย่งสายตาจากปุ่มหลัก

**ปุ่มที่กว้างกว่าปกติกำหนดที่ `className`** เช่นปุ่มเข้าสู่ระบบ `className="h-11 w-48"`
— ปุ่มเดียวของหน้า ควรกดง่ายกว่าปุ่มในตาราง

หรือ `rounded-full` นอกจากไอคอนกลมกับ badge**

## สถานะของช่องกรอก ต้องเห็นได้โดยไม่ต้องอ่าน

| สถานะ | ผู้ใช้เห็น |
|---|---|
| โฟกัส | กรอบเปลี่ยนเป็นสี ring + วงรอบ |
| ผิด | กรอบแดง (`aria-invalid`) + ข้อความใต้ช่อง |
| ปิด | จาง กดไม่ได้ เคอร์เซอร์เป็นห้าม |
| อ่านอย่างเดียว | ตัวอักษรสีปกติ ไม่จาง ไม่มีกรอบโฟกัส |

**`disabled` กับ `readOnly` ไม่เหมือนกัน** — `disabled` แปลว่า "ตอนนี้ยังไม่ถึงตา"
`readOnly` แปลว่า "ค่านี้เป็นแบบนี้ ดูได้แต่แก้ไม่ได้" · ค่าที่แก้ไม่ได้ทำเป็นจางแปลว่า
ผู้ใช้ต้องเพ่งอ่านของที่เราตั้งใจให้เขาอ่าน

**`aria-invalid` ต้องไปถึง `<input>` จริง ๆ** ไม่ใช่ `<div>` ที่ครอบอยู่ —
กรอบแดงผูกกับ attribute นี้ ติดผิดที่แล้วช่องที่กรอกผิดจะดูเหมือนช่องปกติ
(ดูตัวอย่างช่องรหัสผ่านในหน้า login ที่มีปุ่มตาอยู่ข้างใน)

## ข้อความ

**ทุกอย่างที่ผู้ใช้อ่านเป็นไทย** — label ปุ่ม ข้อความ error toast
ยกเว้นชื่อเฉพาะ (`Google` · `Paw Soft`)

**ไม่ต้องมีข้อความในที่ที่ภาพบอกอยู่แล้ว** — ช่องที่ยังว่างขึ้นกรอบแดงพอ
ไม่ต้องเขียน "กรุณากรอกชื่อผู้ใช้" ใต้ช่องที่เห็นอยู่ว่าว่าง
(schema ของหน้า login จึงใส่ข้อความว่างไว้ตั้งใจ)

**ข้อความปฏิเสธมาจาก BE ไม่ใช่จาก FE** — `error.message` เป็นไทยอยู่แล้ว
เอาขึ้น toast ตรง ๆ · FE เขียนเองแปลว่าวันหนึ่งสองที่จะพูดคนละอย่างกับเรื่องเดียวกัน

## toast

`position="top-center"` · `richColors` · 3 วินาที · ตัวเดียวที่ root

| ใช้ | เมื่อ |
|---|---|
| `toast.error` | ทำไม่สำเร็จ · เกือบทุกครั้งคือ `error.message` จาก BE |
| `toast.success` | ทำสำเร็จในสิ่งที่หน้าจอไม่ได้แสดงผลให้เห็นทันที |

**ไม่ toast สิ่งที่หน้าจอบอกอยู่แล้ว** — แถวใหม่โผล่ในตารางแล้วยังเด้ง
"เพิ่มสำเร็จ" ซ้ำ คือการบังหน้าจอเพื่อบอกสิ่งที่มองเห็นอยู่

## หน้าจอต้องใช้ได้บนจอแคบ

ระบบนี้ถูกเปิดบนมือถือหน้างานจริง — ทั้งพนักงานที่ยืนอยู่หน้าเคาน์เตอร์
และเจ้าของสัตว์ที่เปิดดูประวัติจากโทรศัพท์ตัวเอง ซึ่งเกือบทั้งหมดจะเป็นจอแคบ

เรียงบนลงล่างก่อน แล้วค่อยกาง (`flex-col sm:flex-row`) · เส้นคั่นที่มีความหมาย
เฉพาะตอนเรียงแนวนอน ให้ซ่อนตอนจอแคบ (`hidden sm:block`)

**อย่าใส่ความกว้างตายตัวกับสิ่งที่มีข้อความข้างใน** — ข้อความไทยยาวกว่าอังกฤษเกือบเสมอ
